# KIIYA見落としチェッカー 論理データ設計（第1稿）

## 1. 英語の名詞が指すもの

この文書の英語名はデータの種類を表す。画面名や製品名とは区別する。状態名の意味は[状態遷移](state-transitions.md)の冒頭に定義する。

| 英語名 | 日本語で指すもの |
| --- | --- |
| `AppUser` | Googleアカウントでログインするアプリ利用者。社内IT担当者の権限もここで管理する。 |
| `NameSuggestion` | 過去に入力したスタッフ名を、次回の入力候補として表示するための記録。 |
| `MasterRevision` | 客室・設備・清掃項目一式の版。通知の投稿日と成功確認日の遅い方の翌日から有効となり、過去の作業結果を再現できるよう固定する。 |
| `AreaDefinition` | 客室、トイレ、シャワー、洗面、ラウンジなど、清掃箇所の定義。 |
| `ChecklistItemDefinition` | 清掃箇所に適用するチェック項目の文言、表示順、必須区分などの定義。 |
| `WorkRecord` | 1回の清掃作業の記録。作業日、当日の担当職員、休憩、備考、トラブルなどを持つ。 |
| `WorkParticipant` | その`WorkRecord`に参加したスタッフ1名。氏名は当時の入力値として保持する。 |
| `WorkArea` | その`WorkRecord`で選択された、または一度選択された清掃箇所。対象から外しても行を残す。 |
| `WorkAreaAssignment` | どの`WorkParticipant`がどの`WorkArea`を担当したかを表す対応。1箇所に複数人を結び付ける。 |
| `CheckResult` | `WorkArea`内の1つの清掃項目について、確認済みかどうかを記録したもの。 |
| `RoomStay` | 客室の宿泊人数、子どもの人数、連泊、寝具の例外など、客室だけに必要な情報。 |
| `ReportVersion` | `WorkRecord`から作る報告の1つの版。送信時点の内容、宛先、形式、送信結果を固定して残す。 |
| `DeliveryUncertaintyRecord` | 報告の送信結果が一度でも不明になった事実を残す記録。後に投稿結果が判明したり、未送信の報告本文が破棄されたりしても消さない。 |
| `MasterChange` | 設備・清掃項目・客室マスタの変更と、担当職員による承認取得の申告を残す記録。 |
| `Notification` | `MasterChange`をChatworkへ知らせる通知全体の記録。自動再通知を含む送信の経過を束ねる。 |
| `NotificationAttempt` | `Notification`の1回の送信試行。失敗・結果不明・成功を個別の履歴として残す。 |
| `AppAlert` | マスタ変更の通知失敗を、更新操作をしたアプリ利用者本人にだけ知らせるアプリ内の通知。 |
| `ChatworkConfig` | 送信先ルーム、ルーム名、定型文、Markdown送信方法、連携状態などの設定。認証の秘密値は含めない。 |

## 2. 設計の前提

- これは**論理設計**。サーバー環境は選定済みだが、列名、データベース製品、端末側の保存方式は未決定。
- 確定した業務ルールと、実装のための設計案を区別する。「案」と明記した箇所は未確定。
- 入力中の作業記録と、送信時に確定した報告版は別データにする。後から作業記録を直しても、送信済み報告の内容は変えない。
- アプリ利用者のGoogleログインと、当日の担当職員として自由入力した氏名は別の情報。氏名だけを承認者の本人確認やログインIDと見なさない。
- Chatwork投稿の成功が確認できた時点で`WorkRecord`を完了にする。送信失敗・結果不明では完了にしない〔状態遷移で了承済み〕。
- 作業履歴の1週間は、報告結果画面下部の「報告」ボタンを初めて押し、確認ダイアログを開いた時刻から数える。「報告結果画面へ進む」のタップや、ダイアログ内の「完了」は起算点ではない。再送でも起算点は変えない〔決定〕。
- 日付が変わると当日の画面表示を新しい日の初期状態に戻し、前日の`WorkRecord`を過去の記録として設定画面のリンクから閲覧できるようにする。画面表示のリセットは保存済みデータの削除を意味しない〔決定〕。
- 報告ボタン未押下の下書きと送信済み記録は無期限に保管する。押下後も未送信が確定した記録は初回押下から1週間は閲覧でき、その後削除する。送信中・結果不明の版は結論が出るまで削除を保留し、結果不明が発生した事実は本文の削除後も残す〔決定事項を具体化〕。

## 3. データの関係

| 親 | 子 | 関係 |
| --- | --- | --- |
| `AppUser` | `WorkRecord` | 利用者1人が複数の作業記録を作成できる。 |
| `MasterRevision` | `AreaDefinition`・`ChecklistItemDefinition` | 1つのマスタ版に、その時点の箇所と項目を複数持つ。 |
| `MasterRevision` | `WorkRecord` | 作業開始時に有効なマスタ版を1つ固定する。作業中に新版が成立しても自動で差し替えない〔決定〕。 |
| `WorkRecord` | `WorkParticipant`・`WorkArea`・`ReportVersion` | 1回の作業にスタッフ、対象箇所、報告版を複数持てる。 |
| `ReportVersion` | `DeliveryUncertaintyRecord` | 送信結果不明が発生した版の識別子を、独立した事実記録へ写す。未送信の版を破棄しても事実記録は残す。 |
| `WorkArea` | `WorkAreaAssignment`・`CheckResult` | 1箇所に担当者とチェック結果を複数持つ。 |
| `WorkArea` | `RoomStay` | 客室だけに宿泊情報を最大1件持つ。 |
| `MasterChange` | `MasterRevision` | Chatwork通知が成功した変更だけに、新しいマスタ版を対応させる。通知失敗なら新版を作らない。 |
| `MasterChange` | `Notification` | 変更候補を確定したときに通知を作り、適用前に送信結果を確認する。 |
| `Notification` | `NotificationAttempt` | 自動再通知を含む各試行とその結果を個別に保持する。 |
| `MasterChange` | `AppAlert` | 通知失敗・結果不明時に、更新者本人宛のアプリ内アラートを作る。 |

## 4. 主なデータと入力制約

### 4.1 利用者と氏名候補

| データ | 主な項目 | 制約・意味 |
| --- | --- | --- |
| `AppUser` | 内部ID、Googleの識別子、表示名、アプリ内権限、有効状態 | Googleの識別子をログインの照合に使う。メールアドレスや表示名の変更だけで別人扱いしない。Chatwork設定を管理できる社内IT担当者権限を区別する。 |
| `NameSuggestion` | 内部ID、入力された氏名、最後に使った日時 | アプリ利用者全員で共有し、保存期間は無期限〔決定〕。作業履歴1週間の期限では削除しない。 |

### 4.2 マスタ

| データ | 主な項目 | 制約・意味 |
| --- | --- | --- |
| `MasterRevision` | 内部ID、版番号、作成日時、適用開始日、元の版、変更記録への参照 | 通知成功を確認した変更だけから新版を作る。適用開始日は投稿日と成功確認日の遅い方（日本時間）の翌日とし、過去へさかのぼらせない。適用済み版は上書きしない。 |
| `AreaDefinition` | マスタ版、箇所コード、種類、表示名、毎回必須か、定員、ベッド数、ドライヤー有無、表示順 | 箇所コードは版をまたいで同じ場所を指す。定員・ベッド数は客室だけに適用。初期値は203〜206号室、洗面3箇所など要件定義に従う。 |
| `ChecklistItemDefinition` | マスタ版、項目コード、適用箇所または箇所種別、親項目、文言、必須区分、表示順、有効区分 | 階層を表せるようにする。ドライヤー項目は設置箇所にだけ適用する。 |

マスタの「変更前」「変更後」を識別できれば、既に送った報告が後日のマスタ変更で書き換わらない。作業開始時の`MasterRevision`参照を固定し、作業中の自動切替は行わない。適用開始日以降に開始する新しい作業だけが新版を参照する。過去日付のマスタ照会結果も、後日の成功確認で変えない。

マスタ変更候補の下書きは複数あってよいが、**環境ごとに通知中または適用待ちの変更は1件だけ**とする。変更を確定するトランザクションで、`baseRevisionId`がその時点で有効なマスタ版に一致し、ほかに`AwaitingNotification`または`Scheduled`がないことを検査して変更枠を確保する。競合時は`409`を返し、Chatworkへ通知しない。枠は`ChangeFailed`または`Applied`で解放する。待機中に元版が古くなった下書きは、最新マスタを取り込んで変更内容と承認取得を再確認し、新しい変更として作り直す。データベースでも「環境ごとに有効な変更枠は最大1件」と「版番号・適用開始日の重複禁止」を制約として守る。

### 4.3 作業記録

| データ | 主な項目 | 制約・意味 |
| --- | --- | --- |
| `WorkRecord` | 作業ID、作成者、作業日、開始時刻、当日の担当職員名、選択した人数、状態、参照マスタ版、休憩回答、備考、トラブル欄、作成・更新・初回報告ボタン押下・初回完了・過去記録への移動日時 | 人数は1〜5人。休憩回答は「未回答／はい／いいえ」。初回押下時刻は「報告」でダイアログを開いた時に記録し、キャンセル・再送でも上書きしない。日付変更時に過去記録への移動日時を入れる。報告投稿の成功確認で初回完了日時を入れる。 |
| `WorkParticipant` | 参加者ID（UUID）、作業ID、当時入力した氏名、表示順 | 参加者IDは作業内で不変。1作業の人数と参加スタッフ件数を一致させる。名前候補から選んでも新しい参加者IDを発行し、この作業の氏名を独立して保存する。同姓同名でも別IDとする。 |
| `WorkArea` | 作業箇所ID、作業ID、箇所コード、現在の対象区分、初回選択日時、最終変更日時 | 同じ作業IDと箇所コードの組は1件。一度作った行は対象から外しても削除せず、再選択時に再利用する。洗面3箇所とラウンジは常に対象とする。 |
| `WorkAreaAssignment` | 作業箇所ID、参加者ID | 同じ箇所と参加者の組は1件。参加者IDは同じ作業の`WorkParticipant`だけを参照できる。現在の対象箇所には報告前に1人以上必要。 |
| `CheckResult` | 作業箇所ID、項目コード、確認済みか、最終更新日時 | 同じ箇所と項目コードの組は1件。問題の有無ではなく確認完了を表す。対象から外れてもチェックを消さない。 |
| `RoomStay` | 作業箇所ID、宿泊人数、子どもの人数、連泊か、寝具・アメニティの例外記述 | 客室にだけ存在。宿泊人数は0以上かつ客室定員以下、子どもの人数は0以上かつ宿泊人数以下。枕・アメニティ必要数は宿泊人数から算出する。 |

`WorkArea`の「現在の対象区分」は、完了判定、報告書、履歴画面の表示対象に使う。一度対象から外した箇所の`CheckResult`は内部記録に保持する。備考には対象を変更した旨を職員が記入する。報告書と履歴画面には対象区分が有効な箇所だけを表示し、対象外箇所とそのチェック結果は表示しない〔決定〕。

氏名の変更や表示順の変更では参加者IDを変えない。参加者を削除する操作で担当割当が残る場合は、先に割当を外すよう`422`で案内し、別人へ自動で付け替えない。報告版には送信時点の参加者IDと氏名を写す。

送信済みの`ReportVersion`を再表示するときは、その版を確定した時点の対象区分の写しで表示対象を決める。後から`WorkRecord`の対象を変えても、過去に送った報告の表示は変えない。

### 4.4 報告版・送信

| データ | 主な項目 | 制約・意味 |
| --- | --- | --- |
| `ReportVersion` | 報告版ID、作業ID、版の順序、元版ID、状態、送信時の作業内容の写し、確認済み本文、過去日付の報告か、PDF／Markdown、Markdown送信方法、宛先ルームID・表示名、生成物への参照、送信開始・成功・結果確認日時、Chatwork投稿ID、失敗理由 | 宛先・本文・形式・作業内容はダイアログの「完了」で送信を確定する時に固定する。以後は状態と送信結果だけを更新する。再送・修正は新しい版。PDFなどの生成物は報告版と対応付ける。 |
| `DeliveryUncertaintyRecord` | 記録ID、元の作業ID・報告版IDの写し、結果不明になった日時、当時の宛先ルームID、後から判明した結果・確認日時、Chatwork投稿ID（判明した場合） | 結果不明になった時点で作る。後から`ReportVersion`が送信済み／未送信に変わっても、この事実は消さない。元の未送信データが破棄されても残せるよう、報告本文・添付と独立して保存する。 |

- 「版の順序」は同じ作業内で重複させない。表示用の版番号をどう付けるかは未決定。
- 通信圏外では版を送信中にせず、内容を保存して利用者の再確認を待つ。
- 送信結果不明の版を自動再送しない。投稿済み・未投稿が分かった時刻、確認方法、確認した人を記録できるようにする案。
- `Unknown`または`Sending`の版が1件でもある間は、7日の期限が来てもその版の本文・生成物と関連する作業入力を削除しない。結果確定後に保存期限を判定し直す。
- 投稿済みと確認できた時に作業記録を完了にする。送信済みの報告版は新しい版を作っても無期限に保持する。未送信が確定した版の本文・生成物には初回押下から1週間の期限を適用する。
- 作業履歴の起算点は、報告結果画面下部の「報告」を初めて押した時刻。ダイアログをキャンセルしても残し、再送や新版作成で更新しない〔決定〕。
- 送信時に作業日がその時点の暦日より前なら、確認ダイアログで過去日付を明示する。Chatwork本文とPDFまたはMarkdownの報告内容にも「過去日付の報告」であることと作業日を含める。暦日の判定は日本時間で行う設計案。

### 4.5 マスタ変更・Chatwork通知・設定

| データ | 主な項目 | 制約・意味 |
| --- | --- | --- |
| `MasterChange` | 変更ID、環境ID、元版ID、変更種別、変更候補、更新者のアプリ利用者ID・当日の担当職員名、承認取得の自己申告、KIIYA側スタッフ名、別の職員名、状態、申告・通知成功確認・適用開始日時、変更前後のマスタ版 | 承認相手2名の氏名は自由入力。別の職員名が当日の担当職員名と同じなら変更を進められない。環境ごとの変更枠を確保できた1件だけが通知へ進む。通知成功の確認まで新版は作らない。 |
| `Notification` | 通知ID、変更ID、状態、宛先ルームID・表示名、変更IDと変更内容を含む通知本文の写し、投稿日時、成功確認日時、Chatwork投稿ID、次回再通知予定日時、最終結果確定日時、履歴削除予定日時 | 投稿日時と成功確認日時を分けて残す。適用開始日は両者の日本時間の日付の遅い方の翌日。投稿日時を取得できない場合は確認日の翌日。通知本文に固定の適用予定日を書かない。初回送信の失敗・結果不明が確定した5分後から最大2回自動再通知し、成功しなければ変更不成立とする。 |
| `NotificationAttempt` | 試行ID、通知ID、試行番号、送信開始・終了日時、内部結果、履歴表示結果、失敗理由、照合した投稿ID・投稿日時、Chatwork投稿ID | 結果不明は内部結果として保持し、履歴には「送信失敗扱い（結果不明）」と表示する。自動再通知前に直近メッセージで変更IDを照合する案。見つかれば元の投稿日時と照合で成功を確認した日時を別々に保存し、見つからなければ再通知する。照合範囲が限られるため重複投稿の可能性は残る。 |
| `AppAlert` | アラートID、変更ID、宛先のアプリ利用者ID、表示文、作成・確認日時 | 通知失敗・結果不明時に更新操作をした本人だけを宛先にする。他の職員にはこの失敗アラートを表示しない。アプリを閉じていても次回表示できるよう記録する設計案。 |
| `ChatworkConfig` | 設定ID、有効なルームID・取得したルーム名、報告定型文、Markdown送信方法、連携アカウントの表示情報、OAuthクライアントID、資格情報への参照、最終変更者・日時 | Markdown送信方法の初期値は本文記載。有効な送信先は初期版で1ルーム。OAuth 2.0認可コード方式と`offline_access`を使い、投稿用アカウントは対象ルームに参加する既存社員1名のものとする〔決定〕。クライアントシークレットとリフレッシュトークンの値は、画面、報告版、通知、通常ログ、リポジトリに保存しない。 |

## 5. 更新時に守る整合性

1. **自動保存**: 作業IDと子データのIDを維持し、同じ操作の再適用で作業やチェックが重複しないようにする。1台のスマートフォンでの作業を基本とする。
2. **対象変更**: `WorkArea`の対象区分だけを変え、既存の`CheckResult`と担当者の対応は残す。新しく対象になった箇所には、その`WorkRecord`が参照するマスタ版に基づく必須項目を用意する。報告書と履歴画面は対象区分が有効な箇所だけを描画する。
3. **報告確定**: 「報告結果画面へ進む」では画面表示だけを行う。画面下部の「報告」で初回押下時刻を保存して確認ダイアログを開く。ダイアログの「完了」で必須入力・担当者・チェック・人数の制約と宛先を再検証し、内容の写しと宛先を1つの`ReportVersion`へ固定して送信する。送信中の重複操作を防ぐ。
4. **報告後の編集**: `WorkRecord`側の入力は修正できるが、以前の`ReportVersion`の写しは変更しない。未報告の修正があるかは、作業内容の更新番号と最後に送信した版が参照した更新番号から判定する案。
5. **マスタ変更**: 通知前に元版と変更枠をトランザクションで確保する。競合なら`409`で通知しない。通知失敗・結果不明は履歴で送信失敗扱いとし、更新者本人だけにアラートを表示する。失敗・結果不明の判定から5分後に最大2回再通知し、計3回とも成功せず投稿済みとも確認できなければ変更不成立とする。成功を確認した日より前に新版を適用せず、既存作業の参照版は変えない。`ChangeFailed`の後に投稿の証拠が見つかっても変更を自動復活させず、監査記録に残して必要なら最新マスタを元に新しい変更を作る。

## 6. 保存期間と保護

| データ群 | 現時点の扱い |
| --- | --- |
| 報告ボタン未押下の`WorkRecord`と参加者・対象箇所・チェック・宿泊情報 | 下書きとして無期限に保管〔決定〕。日付変更後はアーカイブ閲覧ページから参照できる。報告結果画面を開いただけでは1週間の期限を開始しない。 |
| 報告ボタン押下後で送信済みの`WorkRecord`と子データ | 無期限に保管〔決定〕。日付変更後はアーカイブ閲覧ページから参照できる。 |
| 報告ボタン押下後で未送信が確定した`WorkRecord`と子データ | 初回押下から1週間は保持し、日付変更後はアーカイブから参照できる。送信済み版がなく、保留中の版もなければ期限後に本文・入力結果を削除する〔決定事項を具体化〕。 |
| `ReportVersion`と生成物 | `Sent`の版と本文・生成物は無期限に保管する。`Sending`・`Unknown`の版は結論が出るまで本文・生成物と必要な作業入力を保留し、7日経過で削除しない。`Failed`に確定した版は初回押下から7日後（すでに過ぎていれば直ちに）本文・生成物を削除する。送信済み版が別にあっても、未送信版の本文にはこの期限を適用する。 |
| `DeliveryUncertaintyRecord` | 送信結果不明が一度でも生じた事実を無期限に残す〔決定〕。報告が最終的に未送信と判明しても、結果不明が発生した記録は残す。 |
| `NameSuggestion` | アプリ利用者全員で共有し、保存期間は無期限。作業履歴が1週間を過ぎても候補を自動削除しない〔決定〕。 |
| `Notification`、`NotificationAttempt` | マスタ変更通知の履歴。成功または最大2回の自動再通知後の失敗が確定した時刻から1週間保存し、期限後に削除する〔決定、起算点は設計上の明確化〕。作業履歴1週間とは別の期限。 |
| `MasterRevision`、`MasterChange`、`AppAlert` | マスタ版は過去の報告再現に必要な間保持する。マスタ変更・承認取得記録は1年保存〔決定〕。起算点は通知成功または変更不成立の最終結果確定時刻とする設計案。アラートは確認後30日で削除し、未確認でも作成から最長1年〔決定〕。通知履歴の1週間とは別の期限。 |
| `AppUser`、`ChatworkConfig`、連携資格情報 | アカウント・設定のデータ。作業履歴1週間は適用しない。OAuthクライアントシークレットとリフレッシュトークンはGoogle Cloud Secret Managerに保管する。資格情報の有効期間・失効時の扱いはChatwork OAuth仕様に従い、保管済みの旧版をいつ破棄するかは技術設計で決める。 |

オフライン中の未送信データは端末を閉じても残す。報告ボタン未押下の下書きは無期限に保管し、押下後の未送信が確定したデータは初回押下から1週間後に削除する。送信結果が未確定なら削除を保留し、確認で`Sent`なら無期限保存、`Failed`なら期限を再判定する。結果不明だった事実はどちらの場合も独立して無期限に残す。日付変更による画面リセットとアーカイブへの移動は、期限を早めない。

## 7. 次に決める事項
