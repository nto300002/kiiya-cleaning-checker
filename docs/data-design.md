# KIIYA見落としチェッカー 論理データ設計（第1稿）

## 1. 英語の名詞が指すもの

この文書の英語名はデータの種類を表す。画面名や製品名とは区別する。状態名の意味は[状態遷移](state-transitions.md)の冒頭に定義する。

| 英語名 | 日本語で指すもの |
| --- | --- |
| `AppUser` | Googleアカウントでログインするアプリ利用者。社内IT担当者の権限もここで管理する。 |
| `NameSuggestion` | 過去に入力したスタッフ名を、次回の入力候補として表示するための記録。 |
| `MasterRevision` | 客室・設備・清掃項目一式の版。過去の作業結果を再現できるよう固定する。通知成功だけでは新版を作らない。 |
| `AreaDefinition` | 客室、トイレ、シャワー、洗面、ラウンジ、廊下、階段・玄関、洗面周り廊下の定義。旧「洗面周り床」は新版の箇所マスタに含めず、旧版の参照用定義を保持する。 |
| `ChecklistItemDefinition` | 清掃箇所に適用するチェック項目の文言、表示順、必須区分などの定義。 |
| `WorkRecord` | 1回の清掃作業の記録。作業日、当日の担当職員、休憩、問題発見時の内容を含む備考などを持つ。 |
| `WorkParticipant` | その`WorkRecord`に参加したスタッフ1名。氏名は当時の入力値として保持する。 |
| `WorkProgressCorrection` | 作業単位の開始・完了・時間説明、および客室最終確認・不備を訂正した際の修正前後の値、操作した職員、日時。 |
| `WorkArea` | その`WorkRecord`で選択された客室。対象から外しても行と種別別の回答を残す。 |
| `WorkTaskProgress` | ベッドメイキングなど清掃作業の種類ごとの対象、担当者、開始・終了または時間説明、完了。 |
| `WorkTaskAssignment` | どの`WorkParticipant`がどの清掃作業を担当したかを表す対応。1作業に複数人を結び付ける。 |
| `WorkImageAttachment` | 作業全体の備考に添付した画像と、その保存物への参照。 |
| `CheckResult` | 客室内の1つの清掃項目について、確認済みかどうかを記録したもの。 |
| `RoomStay` | 客室の大人・子どもの人数、3種類の作業、寝具の例外など、客室だけに必要な情報。
| `RoomDefect` | 客室の未解消不備と解消履歴。対象チェック項目と内容を特定する。 |
| `ReportVersion` | `WorkRecord`から作る報告の1つの版。送信時点の内容、宛先、形式、送信結果を固定して残す。 |
| `ReportImageSnapshot` | 報告確定時に備考へ添付されていた画像のIDと保存物への参照を固定したもの。 |
| `DeliveryUncertaintyRecord` | 報告の送信結果が一度でも不明になった事実を残す記録。後に投稿結果が判明したり、未送信の報告本文が破棄されたりしても消さない。 |
| `LateNotificationEvidence` | 不成立となったマスタ変更の通知が後からChatworkで見つかった証拠。変更を復活させず、非適用の理由を追跡する。 |
| `MasterChangeOutcomeAnchor` | 変更内容の保存期限後も、変更IDと最終結果だけを照合する最小限の索引。氏名と変更内容は含めない。 |
| `MasterChange` | マスタ変更候補、別職員1名の承認取得申告と氏名、申請・通知・編集・確認・適用結果を残す記録。 |
| `Notification` | `MasterChange`をChatworkへ知らせる通知全体の記録。自動再通知を含む送信の経過を束ねる。 |
| `NotificationAttempt` | `Notification`の1回の送信試行。失敗・結果不明・成功を個別の履歴として残す。 |
| `AppAlert` | マスタ変更の通知失敗を、更新操作をしたアプリ利用者本人にだけ知らせるアプリ内の通知。 |
| `ChatworkConfig` | 送信先ルーム、ルーム名、定型文、Markdown送信方法、連携状態などの設定。認証の秘密値は含めない。 |

## 2. 設計の前提

- これは**論理設計**。永続データベースにはCloud SQL for PostgreSQLを採用する。列名と端末側の保存・同期方式は未決定。[サーバー環境・秘密情報・権限設計](infrastructure-and-access.md)に配置と費用の前提を記す。
- 確定した業務ルールと、実装のための設計案を区別する。「案」と明記した箇所は未確定。
- 入力中の作業記録と、送信時に確定した報告版は別データにする。後から作業記録を直しても、送信済み報告の内容は変えない。
- アプリ利用者のGoogleログインと、当日の担当職員として自由入力した氏名は別の情報。氏名だけを承認者の本人確認やログインIDと見なさない。
- Chatwork投稿の成功が確認できた時点で`WorkRecord`を完了にする。送信失敗・結果不明では完了にしない〔状態遷移で了承済み〕。
- 作業履歴の1週間は、報告結果画面下部の「報告」ボタンを初めて押し、確認ダイアログを開いた時刻から数える。押下APIを経ずに直接報告確定APIが呼ばれた場合だけ、報告版の作成時刻を初回押下時刻として同じトランザクションで保存する。再送でも起算点は変えない〔決定〕。
- 日付が変わると当日の画面表示を新しい日の初期状態に戻し、前日の`WorkRecord`を過去の記録として設定画面のリンクから閲覧できるようにする。画面表示のリセットは保存済みデータの削除を意味しない〔決定〕。
- 報告ボタン未押下の下書きと送信済み記録は無期限に保管する。押下後も未送信が確定した記録は初回押下から1週間は閲覧でき、その後削除する。送信中・結果不明の版は結論が出るまで削除を保留し、結果不明が発生した事実は本文の削除後も残す〔決定事項を具体化〕。

## 4. 主なデータと入力制約

### 4.1 利用者と氏名候補

| データ | 主な項目 | 制約・意味 |
| --- | --- | --- |
| `AppUser` | 内部ID、Googleの識別子、表示名、アプリ内権限、有効状態 | Googleの識別子をログインの照合に使う。メールアドレスや表示名の変更だけで別人扱いしない。Chatwork設定を管理できる社内IT担当者権限を区別する。 |
| `NameSuggestion` | 内部ID、入力された氏名、最後に使った日時 | アプリ利用者全員で共有し、保存期間は無期限〔決定〕。作業履歴1週間の期限では削除しない。 |

### 4.2 マスタ

| データ | 主な項目 | 制約・意味 |
| --- | --- | --- |
| `MasterRevision` | 内部ID、版番号、作成日時、適用開始日時、元の版、変更記録への参照、確認者ID・確認日時・内容ハッシュ | 確認時に予約版を固定し、翌日0:00（日本時間）に適用する。適用済み版は上書きしない。取下げた予約版も監査用に保持する。 |
| `AreaDefinition` | マスタ版、箇所コード、種類、表示名、毎回必須か、定員、ベッド構成（種別・台数・EX）、ドライヤー有無、表示順 | 箇所コードは版をまたいで同じ場所を指す。客室の初期値は203=ダブル1台・2名、204=シングル4台＋EX1台・5名、205=ダブル2台・4名、206=シングル2台＋EX1台・3名。洗面3箇所、ラウンジ、客室廊下、階段・玄関、洗面周り廊下を新版に定義する。トイレ・シャワーは作業時に個別箇所を指定せず、グループの上限を2・3か所とする。 |
| `ChecklistItemDefinition` | マスタ版、項目コード、適用箇所または箇所種別、客室で適用する作業種別、親項目、文言、必須区分、表示順、有効区分 | 客室の3種類ごとに必要項目を切り替える。共用部の旧詳細項目は現行の報告条件に適用しない。再導入する場合はドライヤー有無などの設備情報で適用を絞る。 |

作業開始時の`MasterRevision`参照を固定し、作業中の自動切替は行わない。ベッド構成の変更では旧版の`AreaDefinition`を更新・削除せず、新しい`MasterRevision`に新しい構成を保存する。アーカイブ詳細は`WorkRecord.masterRevisionId`の客室情報を表示し、送信済み`ReportVersion`は確定時の客室マスタの写しを表示する。通知成功だけでは新しい版を作成せず、過去日付のマスタ照会結果も変えない。確認完了の翌日0:00（日本時間）を新版の適用開始日時とする。

マスタ変更候補の下書きは複数あってよい。環境ごとの通知中の変更は1件に制限し、`submit`時に元版と`AwaitingNotification`の有無を同じトランザクションで検査する。競合時は`409`を返し、Chatworkへ通知しない。通知の成否が確定すると通知枠を解放する。通知済み申請は申請日時順に表示する。編集は更新番号で競合を防ぎ、確認時に現行元版と同じ適用日時の予約を照合する。競合は`409`とし、古い候補は新たな申請・承認からやり直す。通知済み申請を新版として自動適用しない。

### 4.3 作業記録

| データ | 主な項目 | 制約・意味 |
| --- | --- | --- |
| `WorkRecord` | 作業ID、作成者、作業日、予定開始9:55、全体の実開始時刻、当日の担当職員名、人数、状態、参照マスタ版、休憩回答、備考、鍵メモ、シーツメモ、作成・更新・初回報告ボタン押下・初回完了日時 | 開始ボタンの初回操作で実開始時刻をサーバー側で1回固定する。客室別の時計は持たない。鍵・シーツは備考と独立して保存し、更新番号・下書き復元・報告版の写しへ反映する。休憩は未回答／はい／いいえ。初回押下時刻はキャンセル・再送でも変えない。 |
| `WorkParticipant` | 参加者ID（UUID）、作業ID、当時入力した氏名、表示順 | 参加者IDは作業内で不変。1作業の人数と参加スタッフ件数を一致させる。名前候補から選んでも新しい参加者IDを発行し、この作業の氏名を独立して保存する。同姓同名でも別IDとする。 |
| `WorkArea` | 客室ID、作業ID、客室コード、対象区分、職員最終確認・確認者ID・時刻、初回選択・最終変更日時 | 203〜206の客室だけに1件ずつ。対象から外しても行を残す。担当者・開始終了・完了は持たない。宿泊内容やチェックを変更したら最終確認を無効化する。 |
| `RoomDefect` | 端末発行の不変UUID、客室ID、対象項目コード、不備内容、未解消／解消済み、登録・解消日時と操作者ID | 同じIDの状態変更で解消を追跡し、削除・ID再利用・内容の上書きをしない。未解消中は報告不可。解消後も対象チェックと職員最終確認を再確認する。履歴は残す。一般の気づきとの分類基準と画面操作は#58で決める。 |
| `WorkTaskProgress` | 作業ID、作業種別、ユニット、対象客室コード群、対象数、シャワー実施数、実開始・終了、時間説明、完了 | ユニット1はベッドメイキング・アメニティセット・部屋掃除・廊下・階段玄関。ユニット2はシャワールーム・ラウンジ・洗面台・トイレ掃除・洗面周り廊下。作業種別ごとに1件。複数客室と時間帯重複を許す。トイレ対象0〜2、シャワー0〜3、初期値2・3。洗面は全箇所。実施数を入力するのはシャワーだけ。担当1人以上と整合する開始・終了の組、または時間説明が完了条件。片側だけの時刻は不可。 |
| `WorkTaskAssignment` | 作業種別ID、参加者ID | 同じ作業種別と参加者の組は1件。同じ`WorkRecord`の参加者だけを参照し、同姓同名でもIDで区別する。 |
| `CheckResult` | 作業箇所ID、項目コード、確認済みか、最終更新日時 | 客室の作業種別に適用中の項目だけを完了判定・報告に使う。種別や対象を変更しても旧回答は内部に残す。共用部の旧詳細項目は完了判定に使わない。 |
| `RoomStay` | 作業箇所ID、大人人数、子ども人数、作業種別（`checkout`／`stay_amenities_only`／`stay_cleaning`）、寝具の例外記述 | 客室にだけ存在。両人数は0以上、合計は1以上かつ定員以下。大人用スリッパ＝大人、子ども用＝子ども、歯ブラシと枕＝合計人数。枕は`checkout`でセット、`stay_cleaning`で基本的に再セットし、両種別で確認を必須にする。`stay_amenities_only`では枕の作業項目を生成しない。アメニティ設置場所は`stay_amenities_only`のみ玄関靴箱、他は部屋。その他のアメニティ品目はMVPでは扱わない〔暫定方針〕。 |
| `WorkImageAttachment` | 画像ID（UUID）、作業ID、非公開ストレージのオブジェクトキー、MIME形式、バイト数、SHA-256、追加・除外日時 | 画像は作業全体の備考に添付する。画像IDは端末で発行し、再送・自動保存でも維持する。オブジェクトは上書きせず、画像の入れ替えは旧画像の除外と新IDの追加で表す。作業の更新番号を進める。 |

`WorkArea`の「現在の対象区分」は、完了判定、報告書、履歴画面の表示対象に使う。一度対象から外した箇所の`CheckResult`は内部記録に保持する。備考には対象を変更した旨を職員が記入する。報告書と履歴画面には対象区分が有効な箇所だけを表示し、対象外箇所とそのチェック結果は表示しない〔決定〕。

トイレ・シャワーの対象数は清掃範囲画面で変更し、`WorkTaskProgress.targetCount`へ記録する。シャワーだけ実施数を持つ。トイレと洗面台に実施数は保存しない。対象数0のトイレ・シャワーは判定・報告・履歴の表示対象から外す。洗面台は全箇所を1作業として記録する。対象数変更前の入力は変更履歴に残し、現行の報告可能判定・報告書・履歴には現在の対象だけを使う。`washCorridor`は「洗面周り廊下」を表す独立した作業種別とする。新版に`washFloor`は設けない。旧版の「洗面周り床」は当時の写しと参照用マスタを保持し、未送信旧記録から新版の廊下作業へ値を自動転記しない。

旧`WorkArea`の客室別時刻と旧`WorkAreaGroupProgress`の件数・時刻は、移行前の写しとして保存する。複数客室の時刻を新しい作業時刻へ合算・平均しない。トイレ・洗面の旧実施数も新形式の入力項目へ写さない。未送信の旧記録は利用者が作業別記録を確認するまで新形式の報告を確定できないようにし、送信済み旧`ReportVersion`は旧版の写しのまま再表示する。移行前後の`revision`と報告版の参照を維持し、二重記録を作らない。

客室の作業種別を変更した場合、旧種別の`CheckResult`は消去せず、その種別に再切替したときに確認できる。ただし現在の作業種別に適用しない項目は未完了数にも報告版にも含めない。通常清掃の枕セットと連泊清掃の枕再セットは別の項目コードにし、種別変更時に確認済み状態を流用しない。報告版には作業種別、大人・子どもの人数、導出したスリッパ・歯ブラシ数、通常清掃・連泊清掃での枕の必要数と適用中のセット／再セット確認結果、アメニティ設置場所、送信確定時の客室マスタ版ID・定員・ベッド構成、作業種別ごとの対象室・担当者・入力済み開始終了または時間説明、シャワーの対象数・実施数、客室最終確認、鍵・シーツのメモを写す。枕の必要数は保存済みの大人・子どもの合計から導出し、独立した入力値としては保持しない。

氏名の変更や表示順の変更では参加者IDを変えない。参加者を削除する操作で作業種別の担当割当が残る場合は、先に割当を外すよう`422`で案内し、別人へ自動で付け替えない。報告版には送信時点の参加者IDと氏名を写す。

送信済みの`ReportVersion`を再表示するときは、その版を確定した時点の対象区分の写しで表示対象を決める。後から`WorkRecord`の対象を変えても、過去に送った報告の表示は変えない。

撮影・ギャラリー選択した画像はオフライン中も端末内に画像IDとともに保持し、復帰後に非公開のGoogle Cloud Storageへ同期する。APIは認証済みの作業・報告閲覧権限を確認して画像を返し、永続的な公開URLを保存しない。アップロード中または端末にだけ残る画像がある作業は報告を確定できない。画像の追加・除外は専用APIで行い、`PATCH`の文字列欄だけで画像を置き換えない。

### 4.4 報告版・送信

| データ | 主な項目 | 制約・意味 |
| --- | --- | --- |
| `ReportVersion` | 報告版ID、作業ID、版の順序、元版ID、状態、送信時の作業内容の写し、利用者が確認した編集済み本文、最終送信本文、過去日付の報告か、PDF／Markdown、Markdown送信方法、宛先ルームID・表示名、生成物への参照、送信開始・監視期限・成功・結果確認日時、Chatwork投稿ID、失敗理由 | プレビューでは作らず、ダイアログの「完了」で`Sending`の版を初めて作る。編集済み本文はAPIから受け取り、元の作業更新番号の一致を検証する。最終送信本文は必須の報告識別子・過去日付表示と生成した報告内容を加えて固定する。以後は状態と送信結果だけを更新する。 |
| `ReportImageSnapshot` | 報告版ID、画像ID、MIME形式、バイト数、SHA-256、オブジェクトキーの写し | 確定時に有効な`WorkImageAttachment`だけを写す。作業側で後から画像を除外しても過去の報告版から参照できる。PDFの備考欄に縮小画像を埋め込み、Markdownに備考と添付ファイル名を記載し、画像ファイルもChatworkへ個別送信する。 |
| `DeliveryUncertaintyRecord` | 記録ID、元の作業ID・報告版IDの写し、結果不明になった日時、当時の宛先ルームID、後から判明した結果・確認日時、Chatwork投稿ID（判明した場合） | 結果不明になった時点で作る。後から`ReportVersion`が送信済み／未送信に変わっても、この事実は消さない。元の未送信データが破棄されても残せるよう、報告本文・添付と独立して保存する。 |

- 表示用の版番号は作業ごとに`第N版`の単調増加連番とし、本文削除後も番号を再利用しない。
- プレビューは一時データで、`ReportVersion`の`Draft`・`Ready`を永続化しない。版番号は確認ダイアログの「完了」が作業更新番号と必須条件の検証に通り、`Sending`の版を作るトランザクションで割り当てる。キャンセル、プレビュー再生成、検証失敗では消費しない。
- 編集済み本文は確認ダイアログの「完了」で`sourceRevision`とともに受け取る。現在の`WorkRecord.revision`と異なれば`409`とし、再プレビュー・再確認を求める。空文字も利用者の意図した編集値として許すが、送信に必要な報告IDや過去日付表記はサーバーが最終本文に加える。
- 通信圏外では版を送信中にせず、内容を保存して利用者の再確認を待つ。
- 送信結果不明の版を自動再送しない。投稿済み・未投稿が分かった時刻、確認方法、確認した人を記録できるようにする案。
- `Sending`の監視期限は送信開始から5分。1分間隔の監視処理で報告IDをChatworkの直近メッセージと照合し、投稿済みなら`Sent`、確実に未投稿と分かれば`Failed`、それ以外は`Unknown`に確定する。直近に見つからないだけでは`Failed`にしない。監視処理の再起動後も送信開始時刻を基に期限超過を回収する。遅れて到着した成功応答は状態の競合を防いで`Unknown`から`Sent`に確定できる。
- `Unknown`または`Sending`の版が1件でもある間は、7日の期限が来てもその版の本文・生成物と関連する作業入力を削除しない。結果確定後に保存期限を判定し直す。
- 初めて投稿済みと確認できた時に作業記録を`Completed`にする。以後は作業状態を戻さず、送信済み実績の有無、最新版ID・状態、未報告の修正の有無を別に示す。最新版が`Sending`・`Unknown`の間は次の版を送信させず、`Failed`・`Sent`なら現在の入力が準備済みの場合に新版を送れる。送信済みの報告版は新しい版を作っても無期限に保持する。未送信が確定した版の本文・生成物には初回押下から1週間の期限を適用する。
- 作業履歴の起算点は、報告結果画面下部の「報告」を初めて押した時刻。ダイアログをキャンセルしても残し、再送や新版作成で更新しない〔決定〕。
- 送信時に作業日がその時点の暦日より前なら、確認ダイアログで過去日付を明示する。Chatwork本文とPDFまたはMarkdownの報告内容にも「過去日付の報告」であることと作業日を含める。暦日の判定は日本時間で行う設計案。

### 4.6 今回確定した記録と制約

`WorkRecord.createdByUserId`で所有者を判定する。全有効職員が作業・報告・画像を閲覧でき、更新は作成者のみ。同期済みデータは同じGoogleアカウントで復元でき、未同期データは端末紛失時に復元できない。複数端末の更新番号不一致は`409`とする。

`MasterChange`には申請者ID、別職員1名の承認取得申告、承認者氏名、元版ID、候補更新番号、編集者IDの集合と編集履歴、確認者ID・時刻・内容ハッシュ、予約版ID、適用開始日時、取下げ理由を記録する。編集者の集合に含まれるIDは確認者になれない。確認後の再編集は確認を無効化する。

報告の本文・ファイル・各画像は`ReportDeliveryArtifact`として成果物番号、種類、ファイル名、送信用派生物のハッシュ・サイズ、Chatwork投稿ID、送信状態を別々に保持する。PDFと各画像はChatworkの1ファイル5 MB制限を送信前に検証する。一部成功または結果不明なら報告全体を`Unknown`とし、自動再送しない。

## 5. 更新時に守る整合性

1. **自動保存**: 作業IDと子データのIDを維持し、同じ操作の再適用で作業やチェックが重複しないようにする。1台のスマートフォンでの作業を基本とする。
2. **対象変更**: 客室の対象区分を変えても既存の`CheckResult`と不備履歴は残す。新しく対象になった客室には固定マスタ版と作業種別に基づく必須項目を用意し、作業別の対象室を再計算する。トイレ・シャワーの対象数変更は旧数値を履歴に残し、シャワー実施数と完了を再確認する。シャワー実施数が新対象数を超える入力は拒否する。報告書と履歴画面は現在の対象だけを描画する。
3. **報告確定**: 「報告結果画面へ進む」では一時プレビューだけを作る。「編集する」は端末内のプレビュー本文をキャンセルまたはOKで編集し、報告版を作らない。画面下部の「報告」で初回押下時刻を保存して確認ダイアログを開く。ダイアログの「完了」で作業更新番号、編集済み本文、全画像の同期完了、客室チェック・職員最終確認・未解消不備、作業単位の担当・時間、シャワー件数、休憩回答、宛先を再検証し、`Sending`の`ReportVersion`を初めて作る。鍵・シーツのメモも写して固定する。
4. **報告後の編集**: `WorkRecord`側の入力は修正できるが、以前の`ReportVersion`の写しは変更しない。開始・完了の再操作と時刻修正は、当日の担当職員に対応する作成者アカウントだけが行える。修正前後の値、操作したアカウントIDと日時を`WorkProgressCorrection`として追記し、作業のアーカイブ詳細へ表示する。未報告の修正があるかは、作業内容の更新番号と最後に送信した版が参照した更新番号から判定する案。
5. **マスタ変更申請**: 通知前に元版と通知枠をトランザクションで確保する。競合なら`409`で通知しない。通知失敗・結果不明は履歴で送信失敗扱いとし、申請者本人だけにアラートを表示する。失敗・結果不明の判定から5分後に最大2回再通知し、計3回とも成功せず投稿済みとも確認できなければ申請・通知を不成立とする。通知成功では`Notified`とし、新版は作成・適用しない。`ChangeFailed`の後に投稿の証拠が見つかっても自動復活させず、監査記録に残す。

## 6. 保存期間と保護

| データ群 | 現時点の扱い |
| --- | --- |
| 報告ボタン未押下の`WorkRecord`と参加者・対象箇所・チェック・宿泊情報 | 下書きとして無期限に保管〔決定〕。日付変更後はアーカイブ閲覧ページから参照できる。報告結果画面を開いただけでは1週間の期限を開始しない。 |
| 報告ボタン押下後で送信済みの`WorkRecord`と子データ | 無期限に保管〔決定〕。日付変更後はアーカイブ閲覧ページから参照できる。 |
| 報告ボタン押下後で未送信が確定した`WorkRecord`と子データ | 初回押下から1週間は保持し、日付変更後はアーカイブから参照できる。送信済み版がなく、保留中の版もなければ期限後に本文・入力結果を削除する〔決定事項を具体化〕。 |
| `WorkImageAttachment`と画像オブジェクト | 作業から参照する間は作業記録の期限に従う。送信済み報告版の`ReportImageSnapshot`から参照される画像は無期限、`Sending`・`Unknown`の版から参照される画像は結果確定まで保留する。未送信が確定した版だけから参照される画像は初回報告ボタン押下から7日で削除する。作業から除外され、残る報告版の参照もない画像は削除する。複数の版が同じ画像を参照する間はストレージの実体を消さない。 |
| `ReportVersion`と生成物 | `Sent`の版と本文・生成物は無期限に保管する。`Sending`・`Unknown`の版は結論が出るまで本文・生成物と必要な作業入力を保留し、7日経過で削除しない。`Failed`に確定した版は初回押下から7日後（すでに過ぎていれば直ちに）本文・生成物を削除する。送信済み版が別にあっても、未送信版の本文にはこの期限を適用する。 |
| `DeliveryUncertaintyRecord` | 送信結果不明が一度でも生じた事実を無期限に残す〔決定〕。報告が最終的に未送信と判明しても、結果不明が発生した記録は残す。 |
| `NameSuggestion` | アプリ利用者全員で共有し、保存期間は無期限。作業履歴が1週間を過ぎても候補を自動削除しない〔決定〕。 |
| `Notification`、`NotificationAttempt` | マスタ変更通知の履歴。成功または最大2回の自動再通知後の失敗が確定した時刻から1週間保存し、期限後に削除する〔決定、起算点は設計上の明確化〕。作業履歴1週間とは別の期限。 |
| `LateNotificationEvidence` | 不成立後の投稿発見から1年間保存する〔設計レビューで追加〕。元の`Notification`が7日後、`MasterChange`が最終結果から1年後に削除されても、元の変更ID・投稿ID・不成立日時・非適用理由の写しを保持する。 |
| `MasterChangeOutcomeAnchor` | 氏名と変更内容を含まない最小限の最終結果索引を無期限保存する〔設計レビューで追加〕。証拠登録時に元の変更が`ChangeFailed`だったことを照合するために使い、変更候補や承認記録の1年期限は延ばさない。 |
| `MasterRevision`、`MasterChange`、`AppAlert` | マスタ版は参照する`WorkRecord`または`ReportVersion`が残る間、客室のベッド構成を含めて保持する。無期限の下書き・送信済み報告が参照する版は無期限に保持し、旧版を現行値で上書きしない。変更・承認記録は1年保存。適用済み・取下げ済みの予約版と確認者・内容ハッシュは監査用に残す。起算点は通知成功または変更不成立の最終結果確定時刻とする設計案。アラートは確認後30日で削除し、未確認でも作成から最長1年〔決定〕。通知履歴の1週間とは別の期限。 |
| `AppUser`、`ChatworkConfig`、連携資格情報 | アカウント・設定のデータ。作業履歴1週間は適用しない。OAuthクライアントシークレットとリフレッシュトークンはGoogle Cloud Secret Managerに保管する。資格情報の有効期間・失効時の扱いはChatwork OAuth仕様に従い、保管済みの旧版をいつ破棄するかは技術設計で決める。 |

オフライン中の未送信データは端末を閉じても残す。報告ボタン未押下の下書きは無期限に保管し、押下後の未送信が確定したデータは初回押下から1週間後に削除する。送信結果が未確定なら削除を保留し、確認で`Sent`なら無期限保存、`Failed`なら期限を再判定する。結果不明だった事実はどちらの場合も独立して無期限に残す。日付変更による画面リセットとアーカイブへの移動は、期限を早めない。

アプリ上の削除後も、Cloud SQLの標準バックアップには最大14件の日次写し、画像バケットのソフトデリートには最大7日間の復旧用コピーが残り得る。通常の画面/APIからは参照できない。DB復元後は期限切れデータの削除処理を再実行してからアプリを再開する。これは[環境台帳・復旧手順](environment-operations.md)に定めるMVPの復旧猶予であり、即時の物理消去を保証するものではない。
