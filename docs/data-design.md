# KIIYA見落としチェッカー 論理データ設計（第1稿）

## 1. 英語の名詞が指すもの

この文書の英語名はデータの種類を表す。画面名や製品名とは区別する。状態名の意味は[状態遷移](state-transitions.md)の冒頭に定義する。

| 英語名 | 日本語で指すもの |
| --- | --- |
| `AppUser` | Googleアカウントでログインするアプリ利用者。社内IT担当者の権限もここで管理する。 |
| `NameSuggestion` | 過去に入力したスタッフ名を、次回の入力候補として表示するための記録。 |
| `MasterRevision` | ある時点で有効な客室・設備・清掃項目一式の版。過去の作業結果を後から再現するため固定する。 |
| `AreaDefinition` | 客室、トイレ、シャワー、洗面、ラウンジなど、清掃箇所の定義。 |
| `ChecklistItemDefinition` | 清掃箇所に適用するチェック項目の文言、表示順、必須区分などの定義。 |
| `WorkRecord` | 1回の清掃作業の記録。作業日、当日の担当職員、休憩、備考、トラブルなどを持つ。 |
| `WorkParticipant` | その`WorkRecord`に参加したスタッフ1名。氏名は当時の入力値として保持する。 |
| `WorkArea` | その`WorkRecord`で選択された、または一度選択された清掃箇所。対象から外しても行を残す。 |
| `WorkAreaAssignment` | どの`WorkParticipant`がどの`WorkArea`を担当したかを表す対応。1箇所に複数人を結び付ける。 |
| `CheckResult` | `WorkArea`内の1つの清掃項目について、確認済みかどうかを記録したもの。 |
| `RoomStay` | 客室の宿泊人数、子どもの人数、連泊、寝具の例外など、客室だけに必要な情報。 |
| `ReportVersion` | `WorkRecord`から作る報告の1つの版。送信時点の内容、宛先、形式、送信結果を固定して残す。 |
| `DeliveryUncertaintyRecord` | 報告の送信結果が一度でも不明になった事実を残す記録。後に投稿結果が判明したり、未送信の報告本文が破棄されたりしても消さない。 |
| `MasterChange` | 設備・清掃項目・客室マスタの変更と、担当職員による承認取得の申告を残す記録。 |
| `Notification` | `MasterChange`をChatworkへ知らせる1回の通知記録。再通知する場合は別行で追跡する設計案。 |
| `ChatworkConfig` | 送信先ルーム、ルーム名、定型文、Markdown送信方法、連携状態などの設定。認証の秘密値は含めない。 |

## 2. 設計の前提

- これは技術選定前の**論理設計**。列名、データベース製品、端末側の保存方式は未決定。
- 確定した業務ルールと、実装のための設計案を区別する。「案」と明記した箇所は未確定。
- 入力中の作業記録と、送信時に確定した報告版は別データにする。後から作業記録を直しても、送信済み報告の内容は変えない。
- アプリ利用者のGoogleログインと、当日の担当職員として自由入力した氏名は別の情報。氏名だけを承認者の本人確認やログインIDと見なさない。
- Chatwork投稿の成功が確認できた時点で`WorkRecord`を完了にする。送信失敗・結果不明では完了にしない〔状態遷移で了承済み〕。
- 作業履歴の1週間は、報告結果画面下部の「報告」ボタンを初めて押し、確認ダイアログを開いた時刻から数える。「報告結果画面へ進む」のタップや、ダイアログ内の「完了」は起算点ではない。再送でも起算点は変えない〔決定〕。
- 期限後の作業履歴アーカイブと、報告ボタン未押下の下書きは無期限に保管する。押下後の未送信記録はアーカイブに残さず、送信結果不明が発生した事実は残す〔決定〕。
- 日付が変わると当日の画面表示を新しい日の初期状態に戻し、前日の`WorkRecord`を過去の記録として設定画面のリンクから閲覧できるようにする。画面表示のリセットは保存済みデータの削除を意味しない〔決定〕。

## 3. データの関係

| 親 | 子 | 関係 |
| --- | --- | --- |
| `AppUser` | `WorkRecord` | 利用者1人が複数の作業記録を作成できる。 |
| `MasterRevision` | `AreaDefinition`・`ChecklistItemDefinition` | 1つのマスタ版に、その時点の箇所と項目を複数持つ。 |
| `MasterRevision` | `WorkRecord` | 作業開始時に参照するマスタ版を1つ記録する案。既存作業への新マスタ反映方法は未決定。 |
| `WorkRecord` | `WorkParticipant`・`WorkArea`・`ReportVersion` | 1回の作業にスタッフ、対象箇所、報告版を複数持てる。 |
| `ReportVersion` | `DeliveryUncertaintyRecord` | 送信結果不明が発生した版の識別子を、独立した事実記録へ写す。未送信の版を破棄しても事実記録は残す。 |
| `WorkArea` | `WorkAreaAssignment`・`CheckResult` | 1箇所に担当者とチェック結果を複数持つ。 |
| `WorkArea` | `RoomStay` | 客室だけに宿泊情報を最大1件持つ。 |
| `MasterChange` | `MasterRevision` | 適用した変更が新しいマスタ版を作る案。 |
| `MasterChange` | `Notification` | 変更後の通知を1件以上追跡できる。 |

## 4. 主なデータと入力制約

### 4.1 利用者と氏名候補

| データ | 主な項目 | 制約・意味 |
| --- | --- | --- |
| `AppUser` | 内部ID、Googleの識別子、表示名、アプリ内権限、有効状態 | Googleの識別子をログインの照合に使う。メールアドレスや表示名の変更だけで別人扱いしない。Chatwork設定を管理できる社内IT担当者権限を区別する。 |
| `NameSuggestion` | 内部ID、入力された氏名、最後に使った日時 | アプリ利用者全員で共有し、保存期間は無期限〔決定〕。作業履歴1週間の期限では削除しない。 |

### 4.2 マスタ

| データ | 主な項目 | 制約・意味 |
| --- | --- | --- |
| `MasterRevision` | 内部ID、版番号、作成日時、元の版、変更記録への参照 | 適用済み版の内容を上書きせず、新版を作る案。 |
| `AreaDefinition` | マスタ版、箇所コード、種類、表示名、毎回必須か、定員、ベッド数、ドライヤー有無、表示順 | 箇所コードは版をまたいで同じ場所を指す。定員・ベッド数は客室だけに適用。初期値は203〜206号室、洗面3箇所など要件定義に従う。 |
| `ChecklistItemDefinition` | マスタ版、項目コード、適用箇所または箇所種別、親項目、文言、必須区分、表示順、有効区分 | 階層を表せるようにする。ドライヤー項目は設置箇所にだけ適用する。 |

マスタの「変更前」「変更後」を識別できれば、既に送った報告が後日のマスタ変更で書き換わらない。

### 4.3 作業記録

| データ | 主な項目 | 制約・意味 |
| --- | --- | --- |
| `WorkRecord` | 作業ID、作成者、作業日、開始時刻、当日の担当職員名、選択した人数、状態、参照マスタ版、休憩回答、備考、トラブル欄、作成・更新・初回報告ボタン押下・初回完了・アーカイブ日時 | 人数は1〜5人。休憩回答は「未回答／はい／いいえ」。初回押下時刻は報告結果画面下部の「報告」でダイアログを開いた時に記録し、キャンセル・再送でも上書きしない。報告投稿の成功確認で初回完了日時を入れる。 |
| `WorkParticipant` | スタッフID、作業ID、当時入力した氏名、表示順 | 1作業の人数と参加スタッフ件数を一致させる。名前候補から選んでも、この作業の氏名を独立して保存する。 |
| `WorkArea` | 作業箇所ID、作業ID、箇所コード、現在の対象区分、初回選択日時、最終変更日時 | 同じ作業IDと箇所コードの組は1件。一度作った行は対象から外しても削除せず、再選択時に再利用する。洗面3箇所とラウンジは常に対象とする。 |
| `WorkAreaAssignment` | 作業箇所ID、スタッフID | 同じ箇所とスタッフの組は1件。現在の対象箇所には報告前に1人以上必要。 |
| `CheckResult` | 作業箇所ID、項目コード、確認済みか、最終更新日時 | 同じ箇所と項目コードの組は1件。問題の有無ではなく確認完了を表す。対象から外れてもチェックを消さない。 |
| `RoomStay` | 作業箇所ID、宿泊人数、子どもの人数、連泊か、寝具・アメニティの例外記述 | 客室にだけ存在。宿泊人数は0以上かつ客室定員以下、子どもの人数は0以上かつ宿泊人数以下。枕・アメニティ必要数は宿泊人数から算出する。 |

`WorkArea`の「現在の対象区分」は、完了判定と報告対象に使う。一度対象から外した箇所の`CheckResult`は保持する。備考には対象を変更した旨を職員が記入する。対象外になった箇所のチェックを報告書にどう載せるかは未決定。

### 4.4 報告版・送信

| データ | 主な項目 | 制約・意味 |
| --- | --- | --- |
| `ReportVersion` | 報告版ID、作業ID、版の順序、元版ID、状態、送信時の作業内容の写し、確認済み本文、過去日付の報告か、PDF／Markdown、Markdown送信方法、宛先ルームID・表示名、生成物への参照、送信開始・成功・結果確認日時、Chatwork投稿ID、失敗理由 | 宛先・本文・形式・作業内容はダイアログの「完了」で送信を確定する時に固定する。以後は状態と送信結果だけを更新する。再送・修正は新しい版。PDFなどの生成物は報告版と対応付ける。 |
| `DeliveryUncertaintyRecord` | 記録ID、元の作業ID・報告版IDの写し、結果不明になった日時、当時の宛先ルームID、後から判明した結果・確認日時、Chatwork投稿ID（判明した場合） | 結果不明になった時点で作る。後から`ReportVersion`が送信済み／未送信に変わっても、この事実は消さない。元の未送信データが破棄されても残せるよう、報告本文・添付と独立して保存する。 |

- 「版の順序」は同じ作業内で重複させない。表示用の版番号をどう付けるかは未決定。
- 通信圏外では版を送信中にせず、内容を保存して利用者の再確認を待つ。
- 送信結果不明の版を自動再送しない。投稿済み・未投稿が分かった時刻、確認方法、確認した人を記録できるようにする案。
- 投稿済みと確認できた時に作業記録を完了にする。元の報告版は新しい版を作っても保持する（作業履歴の保存期間内）。
- 作業履歴の起算点は、報告結果画面下部の「報告」を初めて押した時刻。ダイアログをキャンセルしても残し、再送や新版作成で更新しない〔決定〕。
- 送信時に作業日がその時点の暦日より前なら、確認ダイアログで過去日付を明示する。Chatwork本文とPDFまたはMarkdownの報告内容にも「過去日付の報告」であることと作業日を含める。暦日の判定は日本時間で行う設計案。

### 4.5 マスタ変更・Chatwork通知・設定

| データ | 主な項目 | 制約・意味 |
| --- | --- | --- |
| `MasterChange` | 変更ID、変更種別、変更前後の内容、更新者のアプリ利用者ID・当日の担当職員名、承認取得の自己申告、KIIYA側スタッフ名、別の職員名、申告・適用日時、変更前後のマスタ版 | 承認相手2名の氏名は自由入力。別の職員名が当日の担当職員名と同じなら適用できない。承認者のログイン記録はMVPで要求しない。 |
| `Notification` | 通知ID、変更ID、状態、宛先ルームID・表示名、通知本文の写し、送信開始・成功・結果確認日時、Chatwork投稿ID、失敗理由 | 更新後に作る。結果不明なら投稿の有無を確認する。失敗後に再通知する場合は元の通知を上書きせず、新しい通知行を作る案。 |
| `ChatworkConfig` | 設定ID、有効なルームID・取得したルーム名、報告定型文、Markdown送信方法、連携アカウントの表示情報、資格情報への参照、最終変更者・日時 | Markdown送信方法の初期値は本文記載。資格情報そのものは画面、報告版、通知、通常ログ、リポジトリに保存しない。認証方式・投稿用アカウント・送信先ルーム数は未決定。 |

## 5. 更新時に守る整合性

1. **自動保存**: 作業IDと子データのIDを維持し、同じ操作の再適用で作業やチェックが重複しないようにする。1台のスマートフォンでの作業を基本とする。
2. **対象変更**: `WorkArea`の対象区分だけを変え、既存の`CheckResult`と担当者の対応は残す。新しく対象になった箇所には、その`WorkRecord`が参照するマスタ版に基づく必須項目を用意する。
3. **報告確定**: 「報告結果画面へ進む」では画面表示だけを行う。画面下部の「報告」で初回押下時刻を保存して確認ダイアログを開く。ダイアログの「完了」で必須入力・担当者・チェック・人数の制約と宛先を再検証し、内容の写しと宛先を1つの`ReportVersion`へ固定して送信する。送信中の重複操作を防ぐ。
4. **報告後の編集**: `WorkRecord`側の入力は修正できるが、以前の`ReportVersion`の写しは変更しない。未報告の修正があるかは、作業内容の更新番号と最後に送信した版が参照した更新番号から判定する案。
5. **マスタ変更**: 承認取得の申告と相手2名の氏名を検証してから変更を適用する。通知結果はマスタ変更の適用結果と分けて管理する。

## 6. 保存期間と保護

| データ群 | 現時点の扱い |
| --- | --- |
| 報告ボタン未押下の`WorkRecord`と参加者・対象箇所・チェック・宿泊情報 | 下書きとして無期限に保管〔決定〕。報告結果画面を開いただけでは1週間の期限を開始しない。 |
| 報告ボタン押下後の`WorkRecord`と参加者・対象箇所・チェック・宿泊情報 | 初回押下から1週間は通常の作業履歴に残し、期限後は無期限にアーカイブ〔決定〕。送信されなかった記録はアーカイブに残さない。 |
| `ReportVersion`と生成物 | 投稿済みの版は、対応する作業履歴とともに期限後アーカイブする**設計案**。送信操作前の版と、未投稿が確定した失敗版の本文・生成物は「未送信」としてアーカイブに残さない設計案。 |
| `DeliveryUncertaintyRecord` | 送信結果不明が一度でも生じた事実を無期限に残す〔決定〕。報告が最終的に未送信と判明しても、結果不明が発生した記録は残す。 |
| `NameSuggestion` | アプリ利用者全員で共有し、保存期間は無期限。作業履歴が1週間を過ぎても候補を自動削除しない〔決定〕。 |
| `MasterRevision`、`MasterChange`、`Notification` | 設定・変更履歴・通知監査のデータ。保存期間は未決定。作業履歴1週間は自動適用しない。 |
| `AppUser`、`ChatworkConfig`、連携資格情報 | アカウント・設定のデータ。作業履歴1週間は適用しない。資格情報は選択する認証方式に合う秘密情報管理に置く。 |

オフライン中の未送信データは端末を閉じても残す。報告ボタン未押下の下書きは無期限に保管し、押下後の未送信データは1週間後のアーカイブには含めない。端末側とサーバー側の保存・同期方法、端末紛失時の復旧方法は技術設計で決める。氏名、宿泊情報、トラブル内容を含むため、端末・通信・サーバーで権限に応じて保護する。

## 7. 次に決める事項

1. 日付変更時に過去の記録をアーカイブ閲覧ページへ移す処理と、報告ボタン初回押下から1週間後の処理の関係。送信されなかった記録を、過去の記録としていつまで閲覧できるか。
2. 作業中にマスタが変更された場合、既存作業へ新版を自動適用するか。自動適用しない場合の手動更新方法。
3. 対象から外した箇所のチェック結果を、報告書と履歴画面にどう表示するか。
4. マスタ変更の通知が失敗した場合の変更内容・再通知の扱い。
5. Chatwork認証方式、投稿用アカウント、送信先ルーム数、連携資格情報の保存方式。
