# 残る要件の決定（2026-10-13）

本書はIssue #4・#5とマスタ編集・確認・適用の決定を記録する。Issue #3の初期構成は[サーバー環境・秘密情報・権限設計](infrastructure-and-access.md)で選定済み。Issue #32は通知成功だけでは新版を適用しない内容に修正済み。

## 1. 作業記録の権限

| 操作 | 作成者 | 作成者以外の有効な職員アカウント | アプリ内IT担当者 |
| --- | --- | --- | --- |
| 作業・アーカイブ・報告版・画像の閲覧 | 可 | 可 | 可 |
| 作業内容と画像の追加・除外・報告確定 | 可 | 不可 | 作成者である場合のみ可 |
| 送信結果不明の確認 | 可 | 不可 | 可。根拠と確認者IDを記録 |

権限はGoogleログインに結び付く`AppUser`のIDで判定し、自由入力した担当者名・参加者名では判定しない。未認証は`401`、有効な職員アカウントでも他人の更新は`403`、存在しない作業IDは`404`とする。全職員への閲覧許可は所属するこのアプリの有効アカウントだけに限り、公開URLを作らない。

## 2. 端末変更・報告版番号

- オンラインでサーバーへ同期済みの作業と報告版は、同じGoogleアカウントで別端末へログインして復元する。端末だけに残る未同期入力・画像は、元端末を失った場合は復元できない。同期状態を画面に表示する。
- 1作業1端末を基本とする。例外的に同じ作業を複数端末で開いても自動マージしない。更新番号が一致しない保存は`409`とし、最新のサーバー内容を示して利用者に再確認・再入力させる。未同期データを無断で上書き・削除しない。
- 報告の表示番号は作業ごとの`第1版`、`第2版`という単調増加の`sequence`とする。確認ダイアログの「完了」で報告版を永続化した時だけ採番する。プレビュー、キャンセル、入力エラーでは採番しない。本文が期限で削除されても番号は再利用せず、履歴には「第2版（本文削除済み）」のように表示する。元版IDも保持する。

## 3. 報告画像

- 備考・トラブルの画像は、PDFでは所属欄ごとに縮小画像と番号を埋め込む。Markdownでは所属欄、番号、添付ファイル名を列挙する。ChatworkへはPDFまたは設定どおりのMarkdown報告とともに、**各画像ファイルも添付**する。Chatwork本文やMarkdownに公開画像URLを載せない。
- 報告版には元画像のID・所属欄・ハッシュ・非公開保存物への参照を固定する。Chatwork送信用に縮小・圧縮した派生画像は元画像と区別し、元画像を上書きしない。表示順は備考、トラブルの順で、各欄内は追加順、同時刻なら画像ID順とする。
- Chatworkのファイルアップロードは1ファイル5 MBまで。送信前にPDFと各画像のサイズを検査し、必要なら派生画像とPDFを縮小・圧縮する。制限内の成果物を作れない場合は送信を開始せず、対象画像を示して利用者に修正を求める。画像を黙って省略しない。[Chatworkファイルアップロード](https://developer.chatwork.com/reference/post-rooms-room_id-files)
- 本文、報告ファイル、画像ファイルの送信結果を報告IDと成果物番号で個別に記録する。すべての必須成果物の投稿が確認できた時だけ`Sent`にする。一部が届いた、または結果を判定できない場合は`Unknown`として自動再送せず、Chatwork上の投稿とファイルを人が確認する。確認者、時刻、根拠を残す。Chatwork側の添付はアプリ内の画像削除では取り消さない。

## 4. マスタの申請・編集・確認・適用

1. 当日の担当職員が変更を起案し、**自分以外の職員1名から承認を得たと自己申告**して、その職員名を記録する。承認者本人のアプリ操作は要求しない。承認申告・職員名がなければ申請確定を`422`で拒否する。自由入力名は本人確認の証拠ではなく、申告の記録である。
2. 申請を確定したら既定のChatwork通知を送る。通知成功は`Notified`であり、新版作成・適用ではない。通知が不成立なら編集・適用へ進めない。
3. `Notified`の申請は、ログイン済みの全職員が現場職員向け画面で編集できる。編集内容は現行マスタとの差分として保存する。編集者の`AppUser` ID、編集日時、元版ID、変更内容を記録する。複数人が編集する場合は更新番号で競合を検知し、古い内容を無断で上書きしない。
4. ログイン済みの**編集に参加していない別の職員**が、編集後の差分と完成版全体を確認する。確認者の`AppUser` ID、確認日時、対象内容のハッシュ、元版IDを記録する。確認者が編集した場合は別の職員による再確認が必要。確認後の編集は確認を無効にする。
5. 確認完了時に新版を不変の`MasterRevision`として作成し、**確認完了の翌日、日本時間0:00**を適用開始日時にする。適用前の新規作業には現行版を使い、適用後に開始する新規作業だけ新版を使う。開始済み作業と送信済み報告は旧版・写しを維持する。通知の投稿日・成功確認日は適用日の起点にしない。
6. 確認確定のトランザクションで元版が現行版であることと、同じ適用日時に別の新版が予約されていないことを検査する。競合時は`409`として確認・適用を確定しない。古い元版の申請は現行版との差分を見直し、必要なら新しい申請と別職員の承認を取得する。通知済み申請は申請日時順に表示するが、自動で連続適用しない。
7. 適用前なら起案者またはIT担当者が理由付きで申請を取り下げられる。確認済みの予約版を取り下げた場合も、版と確認記録を監査用に残し、有効版にはしない。適用後の変更は新たな申請・承認・編集・確認で行う。

申請を承認した別職員と内容確認者は同じ人でもよい。ただし内容確認者はその変更の編集に参加してはならない。実際の氏名・アカウント割当は運用開始時に登録する。
