# KIIYA見落としチェッカー 要件定義（作業版）

更新日: 2026-10-07

出典: [Notion要件定義（初版）](https://app.notion.com/p/KIIYA-3f1ffab34d9681fc9782e51eb8bc4fc2)、[Notion原案](https://app.notion.com/p/KIIYA-3ecffab34d9680aaa118daf53620bb35)、2026-10-06〜07の利用者回答。

このファイルはNotion要件定義を作業用に転記し、利用者が決定した内容を該当箇所に反映したもの。`要確認`、`暫定案`、`推奨運用案`は確定事項として扱わない。

## 1. 目的と対象

- **目的**: B型事業所が請け負うKIIYAの清掃で、清掃範囲、宿泊人数、アメニティ準備、現場確認の見落としを防ぎ、相手企業への再連絡を減らす。作業結果をその場で確認し、報告書をPDF出力してChatworkへ送信できるようにする。
- **利用者**: 現場の職員・清掃担当者。スマートフォンでの利用を前提とする。
- **1回の作業単位**: 作業日、開始時刻、スタッフ人数と氏名、本日の清掃対象、各担当者、チェック結果、宿泊情報、備忘録、報告形式、送信状態を持つ1件の清掃記録。
- **端末とログイン〔決定〕**: 1件の記録は基本的に1台のスマートフォンで完結する。本アプリにはGoogleアカウントでログインする。
- **履歴〔決定事項を具体化〕**: 日付が変わると前日の記録をアーカイブへ移す。報告ボタン未押下の下書きと送信済み記録は無期限に保管する。押下後の未送信が確定した記録は初回押下から1週間後に削除する。送信中・結果不明の版は、投稿の有無が確定するまで本文・生成物と必要な作業入力を保留する。再送では起算点を更新せず、結果不明が発生した事実は本文の削除後も残す。

## 2. 業務フロー・画面

1. **開始画面**: 開始時刻を入力し、スタッフ人数を1〜5人のプルダウンから選ぶ。人数分の氏名を入力欄に手入力する。一度入力した氏名は履歴から選択できる。本日の担当職員も入力し、報告の投稿成功を確認するまで当該職員を「自分」として扱う。設定画面でChatworkのルームID（rid）と定型文を設定でき、アーカイブ閲覧ページへのリンクを置く。
2. **清掃範囲選択画面**: 現場を目視確認し、本日清掃する客室、トイレ、シャワーを複数選択する。未選択箇所は清掃不要としてチェックリストを生成しない。洗面3か所とラウンジは毎回自動追加する。
3. **全体チェックリスト画面**: 選択した客室、共用部、その他を一覧にし、進捗と未完了数を示す。個別画面へ移動でき、戻っても入力値が残る。
4. **個別チェック画面**: 箇所ごとに参加スタッフから担当者を選び、完了チェックを付ける。1箇所に複数人を割り当てられる〔決定〕。客室の宿泊人数、子どもの人数、連泊を入力する。
5. **報告結果画面**: 全体の必須チェックが揃うと「報告結果画面へ進む」ボタンが有効になる。タップすると開始情報、清掃対象、担当者、チェック結果、備忘録を表示する。定型文を初期値とする送信本文を編集・確認し、送信形式をPDFまたはMarkdownから選ぶ。画面下部の「報告」ボタンを押すと確認ダイアログを表示し、そこで「完了」を押したときだけChatworkへ送る。報告ボタンの初回押下時刻を履歴の起算点とする。

## 3. 機能要件

### FR-01 作業開始・スタッフ

- 開始時刻を入力する。スタッフ人数はプルダウンで1〜5人から選び、人数分の氏名を入力欄に手入力する〔決定〕。
- 一度入力した氏名は履歴から選択できる。氏名候補はアプリ利用者全員で共有し、自動的な保存期限を設けない〔決定〕。担当者欄では今回入力・選択した氏名から選ぶ。1箇所を複数人で担当できる〔決定〕。
- 参加者ごとに作業内で不変のIDを持たせ、担当割当は氏名ではなくそのIDを参照する。同姓同名でも別参加者として扱い、氏名変更・表示順変更では割当先を変えない〔設計レビュー対応〕。
- 本日の担当職員を入力した場合、Chatworkへの報告投稿の成功を確認するまで「自分」は当該職員を指す〔決定〕。送信失敗・送信結果不明ではその日の操作を完了にしない。担当職員を途中変更できるかは要確認。
- 人数プルダウンの初期値は要確認。

### FR-02 清掃対象の選択

- 目視確認に基づき、客室・男／女トイレ・左／中／右シャワーを複数選択する。未選択箇所は清掃不要として完了判定に含めない。
- 洗面3か所とラウンジは毎回必須とする。作業途中で清掃対象を変更しても、変更前に付けたチェックは保持する。変更した旨を備考欄に記載する〔決定〕。対象変更時の画面上の確認方法は詳細定義で決める。
- 対象から外した箇所のチェック結果は内部記録には保持するが、報告書と履歴画面には表示しない。現在対象となっている箇所だけを表示する〔決定〕。

### FR-04 客室チェック

- 各部屋で担当者、シーツ交換、床、消毒、ごみ捨て、宿泊人数、人数分のアメニティと枕、寝具セット、アメニティセット、連泊を扱う。
- 宿泊情報は手入力する。子どもの人数は宿泊人数の内数として0〜宿泊人数から選ぶ。連泊はチェックで表す。ダブルシーツなど寝具構成・例外は自由記述に記録する。
- 清掃要否は事前の対象選択で確定し、個別画面に別の「清掃不要」チェックは置かない。

### FR-05 トイレチェック

清掃対象に選んだ男・女トイレそれぞれで担当者を選び、トイレットペーパーの補充、洗浄剤の流れ・泡立ち、床と便器の汚れ、ごみ箱を確認する。

### FR-06 洗面チェック・設備変更

- 洗面3か所それぞれで担当者を選び、ごみ、鏡、ペーパー、石鹸、排水弁、アルコール拭き、乾拭きを確認する。
- ドライヤーの指紋とコードの項目は設置箇所だけに表示する。**トイレ側1か所にはドライヤーなし、シャワー側2か所にはあり**〔決定〕。
- 現場設備を変更する際は、**KIIYA側スタッフと、当日の担当職員以外の職員1名の承認**を得た場合に当日の担当職員が更新できる〔決定〕。MVPでは当日の担当職員が承認を受けたと自己申告し、承認相手2名の氏名を自由入力して記録する。承認者本人によるアプリ操作や本人確認は求めない〔決定〕。
- 変更内容を登録済みのChatwork宛先へ通知し、通知が成功した場合だけ**投稿日と成功確認日の遅い方（日本時間）の翌日**から新版を適用する。通常は送信日の翌日。後から投稿済みと分かった場合は確認日の翌日とし、過去日にさかのぼらせない。既存作業へ新版を自動適用しない〔設計レビュー対応〕。
- 通知失敗・結果不明は送信失敗扱いとして履歴に残し、更新者本人だけにアプリ内アラートを表示する。変更は適用せず、**初回送信に加えて5分間隔で最大2回**自動再通知する。2回とも失敗・結果不明なら再通知を打ち切り、変更不成立とする。再通知で成功した場合も、その投稿日と成功確認日の遅い方の翌日から新版を適用する〔決定〕。結果不明を再通知すると重複投稿の可能性があるため、変更IDによる照合を試みる設計案。通知履歴は最終結果確定から1週間保存する〔決定、起算点は設計上の明確化〕。承認・変更記録は確定から1年、アプリ内アラートは確認後30日で削除し、未確認でも作成から最長1年保存する〔決定〕。

### FR-07 シャワーチェック

対象に選んだ左・中・右シャワーそれぞれで担当者を選び、次を確認する。詳細な文言と階層はNotion原案に合わせる。

- シャンプー類の補充、定位置、手前からボディーソープ・シャンプー・コンディショナーの順序。
- ガラスの水滴と雑巾の繊維、シャワー温度が中央に戻っていること、天井の水滴。
- ドアの隙間、上下パッキンの裏、下レールの水滴。
- 排水口の水滴と髪などの残り、木の足場のアルコール除菌。
- 室外の荷物台と床の除菌、桶と板の除菌および所定位置への設置。

### FR-08 ラウンジチェック

担当者を選び、冷蔵庫の食料、空のごみ箱、ウォーターサーバーの水量、横のUSEDトレー、手前以外の照明の消灯、天井照明のほこり、窓枠・机・椅子・床の汚れを確認する。連泊客の食料は残してよい。

### FR-09 その他

事前決済客の鍵返却と、備品のスリッパの持ち帰り有無を確認する。「休憩が取れたか」を清掃記録に含める〔決定〕。休憩は未回答・はい・いいえを区別し、「いいえ」も回答済みとして扱う。自由記述の備忘録と、問題発見時に内容を追記するトラブル欄を設ける〔決定〕。休憩の回答は報告前の必須項目とする〔決定〕。

### FR-10 進行制御

必須入力と対象箇所の必須チェックが揃うまで「報告結果画面へ進む」を無効化する。未完了項目と場所を示す。確認時に問題が見つかっても、その項目は確認完了として扱い、トラブル欄に追記する〔決定〕。個別画面と全体画面の往復を許し、報告送信時まで戻り・修正できる。

### FR-11 自動保存・オフライン

入力・チェックの変更を自動保存し、通信圏外でも入力と閲覧を続けられる。接続回復後も記録を保持する。報告ボタンを一度も押していない下書きは無期限に保管する〔決定〕。未送信報告は利用者が内容を再確認してから送信する方式が推奨運用案。未送信、送信中、送信済み、送信結果不明を区別して表示する。

### FR-12 報告

- 結果を画面に表示し、PDFまたはMarkdownを選ぶ。PDFは項目階層とチェックボックス、確認済み状態を視覚的に再現して本文とともに添付する。
- Markdownでは同じ項目・状態をテキストにする。送信方法は設定で「Chatwork本文に記載」と「`.md`ファイルを添付」を切り替えられる。初期設定は「Chatwork本文に記載」〔決定〕。
- 画面下部の「報告」ボタンで確認ダイアログを開き、そこで「完了」を押したときだけ宛先、形式、確認済み本文を送信する。ダイアログをキャンセルしても初回報告ボタン押下時刻は保持する。成功、失敗、送信結果不明を区別し、失敗時も期限内は元記録と生成物を保持する。
- 送信時に作業日が過去の日付なら、その旨をダイアログで確認させ、Chatworkへ送る本文とPDFまたはMarkdownの報告内容にも過去日付の報告であることを明記する〔決定〕。

### FR-13 Chatwork設定

開始画面から連携設定へ移動し、送信先ルームID（rid）と定型文を設定する。ridに対応するルーム名を取得し、設定画面で表示・確認できるようにする〔決定〕。同じ設定画面にアーカイブ閲覧リンクを置き、アーカイブ閲覧ページへ移動できるようにする〔決定〕。rid未入力なら送信を止める。定型文は結果画面で編集できる。初期版で有効な送信先ルームは1つに限る〔決定〕。投稿には、当該ルームに参加し投稿権限を持つ既存社員1名のChatworkアカウントを使う〔決定〕。Chatwork OAuth 2.0認可コード方式と`offline_access`を採用し、連携の認証設定と資格情報は社内のIT担当者として登録された人が管理する〔決定〕。サーバーにはGoogle Cloud Run、秘密情報管理にはSecret Managerを採用する〔決定〕。権限分担は[サーバー環境・秘密情報・権限設計](infrastructure-and-access.md)に定める。

採用した方式の実装条件と、秘密情報管理の具体例は[Chatwork認証の実装案](chatwork-auth-plan.md)に記載する。検証用ridは提供済みで、ローカルのテスト設定に保持する。本番で投稿用に使う既存社員の氏名・アカウントと本番ridは、本番手動テスト時に設定する〔決定〕。

### FR-14 アプリのログイン・履歴〔決定〕

本アプリへのログインにはGoogleアカウントを使用する。1件の記録は基本的に1台のスマートフォンで完結する。日付が変わると前日の作業記録はアーカイブ閲覧ページへ移り、設定画面のリンクから閲覧できる〔決定〕。**報告ボタン未押下の下書きと送信済みの記録は無期限に保管する**。押下後の未送信が確定した記録は初回押下から1週間で削除する。送信中・結果不明の版は結果が確定するまで本文と生成物を保留し、`Sent`なら無期限、`Failed`なら初回押下からの期限を適用する。再送でも起算点を更新しない。結果不明が生じた事実は本文の削除後も残す〔設計レビュー対応〕。氏名候補は全員で共有し、無期限に保管する。端末変更時の復旧方法は要確認。

### FR-15 清掃項目・客室マスタの変更〔決定〕

KIIYA側スタッフと、当日の担当職員以外の職員1名の承認を得た場合に、当日の担当職員が清掃項目・客室マスタの変更を申請できる。MVPでは当日の担当職員が承認を受けたと自己申告し、承認相手2名の氏名を自由入力して記録する。承認者本人によるアプリ操作や本人確認は求めない〔決定〕。変更内容を登録済みのChatwork宛先へ通知し、投稿日と成功確認日の遅い方の翌日から新版を適用する。作業中の既存記録は旧版のままにする。通知失敗・結果不明は送信失敗扱いで履歴に記録し、変更を適用せず、更新者本人にだけアプリ内アラートを表示する。初回送信後、5分間隔で最大2回自動再通知し、なお成功しなければ変更不成立とする。通知履歴は最終結果確定から1週間保存する〔決定〕。承認・変更記録は確定から1年、アプリ内アラートは確認後30日で削除し、未確認でも作成から最長1年保存する〔決定〕。

同じ環境で通知中・適用待ちにできる変更は1件だけ。通知を始める前に元版が現在有効な版と一致するかを検査し、変更枠を確保する。競合した変更は通知せず、最新の版を元に変更内容と承認を確認し直す〔設計レビュー対応〕。

### FR-16 日付変更時の画面切替〔決定〕

日付が変わると当日の入力結果を新しい日の画面へ引き継がず、新しい日の初期画面に戻す。前日の作業記録は画面のリセットで消去せず、過去の記録として自動的にアーカイブ閲覧ページから参照できるようにする〔決定〕。未送信記録も期限内はアーカイブ閲覧ページから見られる。過去の作業日を後から送信するときはFR-12の確認と送信内容への明記を適用する。

## 4. データ・判定ルール

- **記録項目**: 作業ID、作業日、開始時刻、スタッフ人数と氏名、本日の担当職員、対象箇所ごとの担当者（複数人可）、宿泊人数、子どもの人数、連泊、休憩取得の状態、チェック状態、備考、トラブル欄、Chatworkのrid、送信本文、送信形式・Markdown送信方法、送信状態。設備・清掃項目・客室マスタの更新には承認相手2名の自由入力した氏名と、担当職員による承認取得の自己申告・更新・通知の記録も必要。
- **回答状態**: 清掃項目は未チェック／チェック済みの二値。チェック済みは問題の有無にかかわらず確認完了を示し、発見したトラブルはアプリ内のトラブル欄に追記する。休憩取得は未回答／はい／いいえを区別し、「いいえ」も回答済み。連泊は有無を表す別のチェックで、未チェックを「連泊なし」と扱う。宿泊人数・子どもの人数・氏名などの必須入力は値の有無で完了判定する。
- **客室の人数制約**: 宿泊人数は定員以下、子どもの人数は0以上かつ宿泊人数以下。枕とアメニティの必要数は宿泊人数と同数とし、連泊による自動補正はしない。寝具構成・例外は自由記述で扱う。
- **清掃不要箇所**: 本日の清掃対象に選ばなかった箇所にはチェックリストを作らず、清掃実施箇所として報告しない。
- **清掃対象の変更**: 変更前に付けたチェックは内部記録に保持し、変更した旨を備考欄に記載する。報告書と履歴画面には変更後の対象箇所だけを表示し、対象外箇所のチェック結果は表示しない〔決定〕。
- **完了条件**: 対象箇所ごとに1人以上の担当者を選び、適用される必須チェックと必須数値入力を完了する。全対象とその他の必須項目が完了したら報告へ進める。備忘録・寝具の例外記述は任意。
- **報告履歴**: 報告作成時点の内容を固定し、送信日時と結果を保存する。報告後の修正・再送は新しい版として扱う〔決定〕。初回「報告」押下時刻を保存し、再送でも更新しない。送信済み版は無期限に残す。未送信が確定した版は初回押下から1週間で本文・生成物を削除するが、`Sending`・`Unknown`の版は結論が出るまで削除を保留する。7日経過後に`Sent`と確定すれば無期限保存、`Failed`と確定すれば本文を直ちに削除する。結果不明となった事実は本文と独立して追跡できるようにする。版番号・元版との紐付け方法は要確認。

## 5. 非機能要件

- スマートフォンの縦画面で、片手でも対象箇所と未完了箇所が分かる。
- オフライン保存後にアプリを閉じても入力が消えない。基本は1台のスマートフォンで作業を完結する。端末紛失時や例外的な複数端末利用時の扱いは要確認。
- 担当者名、宿泊人数、宿泊状況、連絡先設定を保護し、Chatwork認証情報を画面やPDFに露出しない。
- 通信不能時にChatwork送信を成功扱いにせず、送信状態を確認できる。

## 7. 残る確認事項

1. スタッフ人数の選択肢、氏名の手入力と履歴選択、複数人担当は決定済み。氏名候補は全員で共有し、無期限保存〔決定〕。人数の初期値は未決定。
2. ドライヤー設置箇所と設備更新の承認者・更新者・通知先は決定済み。MVPの承認は当日の担当職員による自己申告と承認相手2名の自由入力で記録する。通知の投稿日と成功確認日の遅い方の翌日から新版を適用し、失敗・結果不明では適用せず更新者本人へのアラート、履歴記録、5分間隔で最大2回の自動再通知を行う〔決定〕。通知履歴は最終結果確定から1週間保存する。承認・変更記録は確定から1年、アプリ内アラートは確認後30日で削除し、未確認でも作成から最長1年保存する〔決定〕。
3. 基本1端末、Googleアカウントログイン、日付変更時の過去記録アーカイブ、設定画面からの閲覧、未押下下書きと送信済み記録の無期限保管、押下後の未送信記録の初回押下から1週間後の削除（結果不明は確定まで保留）、結果不明が発生した事実の保持、氏名候補の全員共有・無期限保存は決定済み。再送でも初回起算点を維持する。例外的な複数端末利用と端末紛失時の復旧は未決定。
4. Chatwork連携の認証設定と資格情報の管理者は、社内IT担当者として登録された人。OAuth 2.0認可コード方式と`offline_access`、対象ルームに参加する既存社員1名のアカウント、初期版の有効な送信先1ルーム、ridに対応するルーム名の設定画面表示は決定済み。検証用ridはローカル設定に保持し、本番の投稿用社員とridは本番手動テスト時に設定する。Google Cloud RunとSecret Manager、環境分離と権限設定は選定済み。実際のプロジェクトID・管理担当者は環境構築時に登録する。

## 9. 清掃報告のChatwork送信失敗時の運用案

**推奨方針**: 送信前の不備は検証で止め、明確に未送信の一時的失敗だけ回数を限って再試行する。成否不明なら自動再送せず「送信結果不明」と示す。作業記録、報告本文、形式を端末に保持し、一意の報告IDを表示・送信内容に含めて二重投稿の照合に使う。

| 状況 | 取扱い案 |
| --- | --- |
| rid未入力・形式不正 | 送信を止めて設定へ誘導する。ridを数値として検証し、可能ならルーム名を表示する。 |
| 認証失敗（401） | 未送信として保持し、再接続・認証情報更新を案内する。自動再試行しない。 |
| 投稿権限不足（403） | 未送信として保持し、ルーム参加・投稿権限・必要なAPI権限の確認を案内する。別ルームへ自動変更しない。 |
| 入力不正・PDFサイズ超過（400等） | 本文とPDFサイズを送信前に確認する。Notion要件定義に記載されたファイル上限は5MB。同じ内容を自動再試行せず、再生成・縮小または手動出力を案内する。 |
| 利用回数制限（429） | 「送信待ち」と表示し、APIのリセット時刻を目安に回数を限って再試行する。上限後は手動再送へ切り替える。 |
| 通信圏外 | 記録と生成物を保持して「未送信」と表示する。接続回復後、利用者が内容を再確認して送信する案。 |
| タイムアウト・接続断・サーバー障害 | 「送信結果不明」と表示し、自動再送しない。報告IDで送信先を確認し、未投稿と確認できた場合だけ再送する。 |
| 連打・二重送信 | 送信中はボタンを無効化し、報告IDと送信状態を記録する。成功済み報告の修正・再送は新しい版として扱う。版番号と元版との紐付け方法は要確認。 |

**API利用案**: PDFはファイルアップロードAPIの`message`欄に確認済み本文を付け、PDFと本文を1回で送る。MarkdownをChatwork本文として送る設定の場合は、確認済み本文とレポートのテキストを合わせ、メッセージ投稿APIで1回送る。`.md`添付を選んだ場合はMarkdownファイルと確認済み本文を送る。Chatwork上でMarkdownが装飾表示されることは前提にしない。
