# KIIYA見落としチェッカー API設計（第1稿）

## 1. 英語名の意味

| 名称 | 意味 |
| --- | --- |
| `WorkRecord` | 1回の清掃作業の入力記録。 |
| `WorkParticipant` | 作業に参加する1人。作業内で変わらないIDと、その時の氏名を持つ。 |
| `WorkImageAttachment` | 備考に添付した作業画像と非公開保存物への参照。 |
| `ReportImageSnapshot` | 報告確定時の備考画像と保存物への固定参照。 |
| `MasterRevision` | 客室・設備・清掃項目の固定された版。 |
| `ReportVersion` | 送信確定時の作業内容と送信先を固定した報告の版。 |
| `MasterChange` | マスタ変更候補、別職員1名の承認申告、編集・確認・適用記録。 |
| `NotificationAttempt` | マスタ変更通知の1回のChatwork投稿試行。 |
| `LateNotificationEvidence` | 不成立後に見つかったマスタ変更通知の証拠と、非適用の理由。 |
| `Idempotency-Key` | 通信再試行や連打による同一操作の重複を防ぐキー。 |
| `revision` | 作業記録の更新番号。競合更新の検出に使う。 |

機械可読の契約は[OpenAPI定義](../api/openapi.yaml)に置く。APIの実装は`server/`に置き、認証・保存・報告・通知などを自動テストで確認する。実環境のGoogle Cloud・Chatwork連携は環境構築後に確認する。

## 2. 認証・権限・時刻

- 公開APIはGoogleログインのIDトークンを受け、サーバーで署名、発行元、audience、有効期限を検証する。`/v1/me`でアプリ内権限を返す。
- Chatwork設定とOAuth接続操作は登録済みIT担当者のみ。OAuthクライアントシークレットとリフレッシュトークンはレスポンスへ出さず、Google Cloud Secret Managerで扱う。
- 全有効職員は他人の作業・報告版・画像も閲覧できる。作業内容・画像の更新と報告確定は作成者IDに限る。開始・完了の再操作と時刻修正も、当日の担当職員に対応する作成者IDだけに許す。自由入力の氏名だけでは権限を与えない。未認証は`401`、他人の更新は`403`、存在しないIDは`404`。
- 報告結果不明の確認は、その作業を作成して「当日担当職員」を入力したログイン利用者、またはIT担当者に許可する。自由入力の氏名だけで本人確認せず、サーバーが記録した作成者IDで照合する。
- OAuthコールバックは`state`とPKCEに加え、接続を開始したIT担当者のログインセッションに結び付けて検証する。
- 業務日と過去日付判定は`Asia/Tokyo`。APIの時刻はUTCオフセット付きRFC 3339、作業日は`YYYY-MM-DD`。
- 作業記録は当日または過去の作業日で作成し、未来の日付では作成しない。当日担当職員によるマスタ変更申請の確定は作業日が当日の記録だけから行う。
- 開始済み作業の`masterRevisionId`は変えない。客室のベッド構成を含む旧マスタ版は参照する作業・報告版が残る間保持する。通知成功だけでは新版を作成・適用しない。全職員がマスタ編集画面を利用でき、編集に参加していない別職員が確認した翌日0:00（日本時間）に新版を適用する。
- `WorkRecord.status=Completed`は送信済み実績を表し、後の修正・再送では戻さない。最新版の送信結果は`latestReportStatus`、未報告の修正は`hasUnreportedChanges`で別に示す。

## 3. 主なAPI操作

| 操作 | 用途・要点 |
| --- | --- |
| `GET /v1/me`、`GET /v1/name-suggestions` | 利用者情報と全員共有の氏名候補を取得。候補は無期限保存。 |
| `GET /v1/master-revisions/current?workDate=...` | 作業日に有効なマスタを取得。作業開始後の自動切替なし。 |
| `POST /v1/work-records` | 作業を開始し、マスタ版、予定開始9:55、サーバー時刻による全体の実開始`actualStartedAt`を1回固定する。人数は1〜5人。参加者は氏名とUUIDを別に持つ。 |
| `GET/PATCH /v1/work-records/{workId}` | 入力中の作業を取得・保存。`revision`一致で更新。当日の担当職員は作業開始時に固定し、`PATCH`で変更しない。客室の大人・子ども・3値の作業種別、客室別チェック・職員最終確認・不備、`workTasks`の作業別担当・時間・完了、トイレ／シャワーの対象数、シャワーの実施数、鍵・シーツのメモを更新する。客室別の担当・時刻、トイレ／洗面の実施数は受け付けない。対象・種別を変えても旧チェックは編集用データに保持。 |
| `GET /v1/work-records/{workId}/history` | 過去記録画面用。対象から外した箇所とチェックは含めない。進捗訂正履歴、固定した`masterRevisionId`と、その版から取得した当時の客室定員・ベッド構成を返す。 |
| `GET /v1/work-records?archived=true` | 設定画面のリンク先で表示する過去記録一覧。日付変更で過去扱い。 |
| `GET /v1/work-records/{workId}/readiness` | 現在対象の客室チェック・職員最終確認・未解消不備、作業別の担当・完了・時間記録、シャワーの実施数と対象数の一致、客室の大人・子ども、休憩回答を検査。`missing`は客室番号・項目コードまたは作業種別を付けて返す。共用部の旧詳細チェックは求めない。 |
| `POST /v1/work-records/{workId}/images`、`DELETE /v1/work-records/{workId}/images/{imageId}` | 備考画像を個別に追加・除外。画像IDと作業更新番号を維持し、本文の`PATCH`とは別に同期する。 |
| `GET /v1/work-records/{workId}/images/{imageId}/content` | 閲覧権限を確認して非公開画像を返す。送信済み報告版が参照する画像は作業側で除外後も取得可能。 |
| `POST /v1/work-records/{workId}/report-preview` | 結果画面用の一時プレビュー。客室の作業種別・数量・配置先、作業単位の担当・入力済み時刻または時間説明、職員最終確認、鍵・シーツのメモを含む。押下時刻、永続報告版、版番号を作らず、初期の編集可能本文とPDF・Markdownの表示内容を取得する。「編集する」のOKは端末のプレビュー本文を更新し、キャンセルは破棄する。 |
| `POST /v1/work-records/{workId}/report-button-press` | 結果画面下部の「報告」で呼ぶ。初回のみ押下時刻を記録し、確認ダイアログを開く。キャンセルは追加API不要。 |
| `POST /v1/work-records/{workId}/report-versions` | ダイアログの「完了」で編集済み本文と作業更新番号を受け取り、再検証後に`Sending`の新版を初めて作る。画像も送信時点で固定。過去日付は明示的な確認値を必要とする。 |
| `GET /v1/work-records/{workId}/report-versions`、`GET /v1/report-versions/{reportId}` | 版と送信結果を取得。送信結果不明時の自動再送はしない。 |
| `POST /v1/report-versions/{reportId}/verification` | 不明結果の確認結果を登録する。当日担当職員またはIT担当者が確認できる。確認者・日時・根拠を残す。 |
| `GET/PUT /v1/settings/chatwork` | IT担当者が接続状態、唯一のルームID・取得したルーム名、Markdown送信方法を確認・更新。 |
| `POST /v1/settings/chatwork/oauth/start`、`GET /v1/settings/chatwork/oauth/callback` | Chatwork OAuth認可コード方式、`offline_access`で接続。stateとPKCEを検証。 |
| `POST /v1/master-changes`、`POST /v1/master-changes/{changeId}/submit` | 変更候補を記録し、`submit`で当日担当職員が別職員1名の承認取得を自己申告して氏名を記録する。元版照合と環境ごとの通知枠確保に成功した場合だけ通知を開始し、競合なら`409`。 |
| `PATCH /v1/master-changes/{changeId}/candidate`、`POST /v1/master-changes/{changeId}/request-review`、`POST /v1/master-changes/{changeId}/confirm`、`POST /v1/master-changes/{changeId}/withdraw` | 通知済み候補を全職員が編集。編集参加者以外の職員が差分と完成版を確認し、翌日0:00適用の不変版を予約。確認後の編集は再確認を要し、競合・古い元版は`409`。適用前の取下げは申請者またはIT担当者のみ。 |
| `GET /v1/master-changes/{changeId}`、`GET /v1/alerts` | 変更状態・通知試行結果と本人宛アラートを表示。 |
| `GET/POST /v1/master-notification-evidence` | IT担当者が不成立後に発見した通知の証拠を変更IDで登録・照会。元の変更記録の削除後も、最小限の最終結果索引と照合する。 |

## 4. 共通規則

1. `PATCH`は`revision`を必須とし、現在値と違う場合は`409`で最新値を返す。上書きは行わない。基本は1端末だが、通信再試行にも必要。
2. 作成・報告確定・マスタ変更確定は`Idempotency-Key`を必須とする。同一利用者・同一操作・同一キー・同一本文なら同じ結果を返し、本文が異なれば`409`。保持期間は実装時に決める。
3. レスポンスの`202`は処理受付を表し、Chatwork投稿成功を意味しない。クライアントは状態取得で`Sent`を確認して初めて完了表示する。
4. 報告ボタンの初回押下時刻は再押下や再送で更新しない。押下APIを経ずに報告確定APIが呼ばれても、版作成と同じトランザクションで初回押下時刻を固定する。未送信が確定した内容は7日後に削除するが、`Sending`・`Unknown`の版は結果確定まで本文・生成物と必要な作業入力を保留する。7日経過後の確認で`Sent`なら無期限保存、`Failed`なら直ちに本文を削除する。結果不明の事実は独立して無期限保存。
5. 対象箇所を外してもチェックは削除しない。報告版・履歴表示には送信確定時または現在の対象箇所だけを含める。対象変更を備考に記載する運用を画面で促す。備考が空欄なら報告を拒否するかは未決定であり、現時点のMVP契約には必須検証を追加しない。
   客室の清掃種別を変更した時は、旧種別の回答を種別別の内部履歴に移し、変更操作に同梱されたチェック値は採用しない。新種別の回答は次の更新で入力する。同じ種別を再選択した場合は、その種別で記録した回答を復元する。報告版の写しには現行種別の回答のみを含める。
6. マスタ変更の通知失敗・結果不明は本人だけにアラートを表示する。5分間隔で最大2回再通知し、計3回成功しなければ変更不成立。結果不明の再通知前に変更IDで投稿済み照合を行う。通知試行履歴は最終結果から7日保存。
7. マスタ変更・承認申告と承認者氏名は最終結果から1年保存する。アラートは確認後30日で削除し、未確認でも作成から1年を上限とする。
   1年の起算点は、通知成功または変更不成立の最終結果が確定した時刻とする設計案。
8. 投稿先は環境ごとに有効な1ルーム。検証用の具体的なridは公開ドキュメントとAPI例に書かない。本番の投稿用社員とridは本番手動テスト時に設定する。
9. オフラインでは端末内に入力を保持し、オンライン復帰後に同期する。オフライン中に「完了」は送信開始と見なさず、利用者の再確認後にAPIを呼ぶ。同期済みデータは同じGoogleアカウントで復元し、端末だけの未同期データは端末紛失時に復元できない。端末保存方式は技術設計で選ぶ。
10. 参加者IDはクライアントが作るUUIDで、作業内で不変とする。氏名候補を選んでも新しい参加者IDを作り、作業種別の担当者は`assigneeIds`で参照する。サーバーは同じ作業の参加者IDか検証し、氏名の重複を許す。担当中の参加者を削除するときは先に割当解除を求める。
11. マスタ変更の下書きは複数作れるが、環境ごとに`AwaitingNotification`は最大1件。`submit`のトランザクションで現在有効な元版と変更枠を検査・確保してから通知する。競合で通知は送らない。`Notified`または`ChangeFailed`で通知枠を解放する。通知済み申請は申請日時順に表示し、編集には候補更新番号を用いる。確認時に現行元版と同日予約を照合し、競合時は`409`。古い候補は新たな申請・承認からやり直す。`ChangeFailed`後の遅い投稿発見では旧変更を復活させない。
12. 初回の`Sent`で`hasSentReport=true`と`Completed`を固定する。最新版が`Sending`・`Unknown`なら次の版の送信は`409`、`Failed`・`Sent`なら準備判定を通して新しい版を送れる。旧版の送信済み実績は最新版の失敗で消えない。
13. `ReportVersion`の送信開始時刻と5分後の監視期限を永続化する。1分間隔の監視で期限超過を拾い、報告IDで投稿を照合する。肯定的な投稿証拠がなければ、直近メッセージに見つからないだけで未投稿とせず`Unknown`にする。ワーカー再起動後も監視を続け、自動再送はしない。
14. `LateNotificationEvidence`はIT担当者の照合記録または自動検知から作る。変更IDが`ChangeFailed`だったことを、変更記録または氏名・変更内容を含まない`MasterChangeOutcomeAnchor`で確認する。同じ変更ID・投稿IDの重複を防ぐ。証拠は発見から1年、最終結果索引は無期限保存し、元の変更状態・マスタは変えない。
15. 端末で撮影・選択した備考画像にはUUIDを発行し、オフライン中は端末に保持する。オンライン復帰後、作業更新番号と冪等キーを付けて非公開ストレージへ同期する。APIは画像ID・MIME形式・サイズ・ハッシュを返し、保存先キーや公開URLは返さない。画像の追加・除外で作業の内容更新番号を進める。報告確定では端末の全添付画像IDを`clientImageIds`で送り、サーバーの同期済み画像ID集合と一致しない場合は`422`で止める。
16. `report-preview`が返す`defaultEditableBody`は結果画面の本文入力欄の初期値。利用者が編集した`confirmedBody`を報告確定APIへ必ず渡す。`sourceRevision`は作業内容の更新番号で、本文・画像の変更では進むが初回報告ボタン押下や送信状態変更だけでは進まない。不一致なら`409`で再プレビューを求める。サーバーは編集済み本文と、報告ID・過去日付表示など必須要素を加えた最終本文を版に固定する。
17. プレビューは一時データであり、永続化する`ReportVersion`の状態は`Sending`から始まる。版番号は作業ごとの単調増加連番を確定トランザクションで割り当て、プレビュー再生成・ダイアログキャンセル・検証失敗では消費しない。本文削除後も番号は再利用しない。
18. 客室の`roomStay`は`adults`、`children`、`workType`を必須とし、合計人数をマスタ定員以下で検証する。初期定員は203=2、204=5、205=4、206=3名。`workType`は`checkout`／`stay_amenities_only`／`stay_cleaning`。スリッパ・歯ブラシ数とアメニティ設置場所はサーバーが導出し、端末から独立した確定値として受け取らない。枕の必要数も大人・子どもの合計から導出し、`checkout`では枕セット、`stay_cleaning`では枕再セットの確認項目を必須とする。`stay_amenities_only`では枕の項目と必要数を表示・報告しない。枕の必要数は既存の`totalGuests`と同じ値なので、独立した確定入力は追加しない。
19. `WorkArea`は客室の対象・宿泊情報・種別別チェック・職員最終確認・不備を保持し、客室別担当者・開始終了時刻を持たない。`WorkTaskProgress`はユニット1のベッドメイキング／アメニティセット／部屋掃除／廊下／階段・玄関掃除、ユニット2のシャワールーム／ラウンジ／洗面台／トイレ掃除／洗面周り廊下を1作業種別につき1件保持する。担当者ID、対象室番号、開始・終了、時間説明、完了を作業単位で保存し、作業間の時間重複を許す。トイレ0〜2・シャワー0〜3の対象数は範囲画面で変更し、初期値は2・3。洗面台は全箇所。実施数入力はシャワーだけに設け、完了時は対象数と一致させる。対象数0のトイレ・シャワー作業は判定・報告から除く。作業の完了には担当者1人以上と、開始・終了の整合した組、または時刻を確定できない理由・進め方を示す`timeDescription`を求める。片側だけの時刻や終了＜開始は`422`。時刻を推測して補完しない。開始・完了の再操作と訂正は作成者だけに許し、修正前後・操作者・日時を残す。

20. 報告確定前にPDFと各送信用画像を生成し、Chatworkの1ファイル5 MB制限を検査する。圧縮しても収まらなければ`422`で送信を止める。PDFには備考画像を埋め込み、Markdownには備考と添付ファイル名を列挙し、画像ファイルは個別に送る。本文・報告ファイル・各画像の送信状態を個別に保持し、すべての必須成果物を確認できた時だけ`Sent`にする。一部成功または結果不明は`Unknown`とし、自動再送せず人が全成果物を照合する。
21. 確認済みのマスタ候補を後から編集した場合は確認を無効化し、再確認を必須にする。確認者の`AppUser` IDがその候補の編集者ID集合に含まれる場合は`403`。確認時に元版・候補更新番号・内容ハッシュ・同日適用予約をトランザクションで照合し、競合は`409`。確認翌日の日本時間0:00から新規作業へ適用する。

### 2026-10-16 現場フィードバックのAPI契約

- `GET/PATCH /v1/work-records/{workId}`の`areas`は客室だけを表し、203→204→205→206の固定順を画面へ返す。客室ボタンで表示する対象室を切り替えてもAPI上の画面状態は変えず、客室コードをキーにした回答を保存する。独立した客室詳細APIは設けない。
- 客室の`finalConfirmed`はログイン中の当日担当職員による操作としてサーバーが`finalConfirmedByUserId`と`finalConfirmedAt`を記録する。宿泊人数・作業種別・必須チェックを変更したら確認を無効化する。項目は問題を見つけても確認済みにできるが、別途登録された未解消の`RoomDefect`がある間は`readiness.ready=false`とする。`RoomDefect`には端末発行の不変UUID、対象項目、内容、状態、サーバー記録の登録・解消日時と操作者を持たせる。同じIDの`open`→`resolved`で解消し、削除やID再利用を認めない。`roomCode`と`checkCode`を不足理由に返し、解消後も対象チェックと最終確認の再操作を必要とする。一般の気づきは備考に残す。両者の分類基準と具体的な登録・解消操作は#58で確定する。
- `workTasks`の客室対象は、選択済み客室と作業種別から導出する。ベッドメイキング・部屋掃除は室内作業がある客室、アメニティセットは対象客室を結び付ける。対象室の変更時は対象一覧を再計算し、担当・時刻・完了の旧値は訂正履歴に残す。対象から外れた客室は現在の報告・履歴表示に含めない。
- 新版の`workTasks.kind`は`washCorridor`を使用し、`washFloor`を設けない。旧版の「洗面周り床」の入力・送信済み報告は当時の形式で保持する。未送信の旧記録から新版へ移行するとき、旧床の値を廊下作業の担当・時刻・完了に自動転記せず、利用者の確認を求める。
- 客室を一室も選ばない場合と、選択客室がすべて「連泊（アメニティのみ）」の場合のベッドメイキング・部屋掃除の必須判定は未決定。対象室が空の作業を判定対象から外す案は#58で比較・決定し、それまでは実装・受け入れで確定規則として扱わない。
- `report-preview`、`ReportVersion`の写し、アーカイブAPIは全体の実開始時刻、作業別の対象・担当・入力済み時刻または`timeDescription`、客室最終確認、鍵メモ、シーツメモを同じ構造から生成する。シャワーだけ対象数・実施数を載せ、トイレは対象数のみ、洗面は全箇所と表す。`sourceRevision`の一致を確定時に再検査し、既存の版固定・保存期限規則を維持する。
- 既存の`WorkArea`/`WorkAreaGroupProgress`からの移行では、客室別時刻を新しい作業時刻へ機械的に合算しない。重複・欠損・矛盾がある旧データは元の写しを保持し、利用者の確認または`timeDescription`による記録まで新形式の報告を確定しない。送信済み旧版は元の契約で再表示し、内容を書き換えない。サーバー実装とDBマイグレーションは#8・#13・#16・#22・#29で扱う。
