# KIIYA見落としチェッカー テストケース

## 1. 前提

- 対象は[API定義](../api/openapi.yaml)と[状態遷移](state-transitions.md)。ここに記すのは受け入れ・結合テスト仕様であり、実行結果は`server/test/`の自動テストと検証環境の記録で管理する。実環境を使うケースは未検証のまま残る。
- 日付は`Asia/Tokyo`の固定時計で検証する。Chatworkは通常モック化し、成功・明確な失敗・タイムアウト・投稿済み照合を再現する。
- 実際のChatwork投稿は検証環境で別途手動テストする。提供済みの検証用ridは無視しないが、公開リポジトリに値や資格情報を書かない。本番の社員アカウントとridは本番手動テスト時に設定する。
- 各ケースの「期待結果」はAPI応答、永続化結果、画面に必要な表示データまで確認する。権限テストは別利用者のトークンで行う。

## 2. 認証・設定

| ID | 操作・条件 | 期待結果 |
| --- | --- | --- |
| AUTH-01 | 有効なGoogle IDトークンで`GET /v1/me` | 利用者IDとロールを返す。 |
| AUTH-02 | 無効・期限切れ・audience違いのトークン | `401`。入力や設定を返さない。 |
| AUTH-03 | 一般職員がChatwork設定更新・OAuth開始 | `403`。設定と秘密情報は変わらない。 |
| AUTH-04 | IT担当者がOAuthを開始し、正しいstateでコールバック | `offline_access`を含む認可フローで接続。秘密値はSecret Managerへ保存し、API応答・URL・通常ログへ出さない。 |
| AUTH-05 | OAuthコールバックでstate不一致または再利用 | 接続拒否。既存連携は変わらない。 |
| AUTH-06 | ルームIDを登録 | Chatworkから取得したルーム名を設定画面用応答に表示。有効な送信先は1ルームだけ。 |
| AUTH-07 | Markdown送信方法を未設定のまま取得、次に添付へ変更 | 初期値は本文記載。変更後は`.md`添付を選択し、PDF設定には影響しない。 |

## 4. 報告と履歴

| ID | 操作・条件 | 期待結果 |
| --- | --- | --- |
| REP-01 | 必須チェック未完了で結果画面へ進もうとする | 進む操作を無効化。不足項目を示す。 |
| REP-02 | 必須項目を揃えて結果画面を開くだけ | `Ready`のまま。初回報告ボタン押下時刻は空。 |
| REP-02A | PDFまたはMarkdownのプレビューを生成 | 現在の作業内容を表示し、初回押下時刻と報告版は作らない。 |
| REP-02C | プレビューの「編集する」で変更してキャンセル／OK | キャンセルは元本文のまま、OKは編集後本文を表示。どちらも報告版・版番号を作らない。 |
| REP-02D | プレビューの客室数量と作業別記録を確認 | 備品数、作業種別、配置先、作業別担当・入力済み時間または説明、シャワーの対象／実施数、トイレ対象数、鍵・シーツのメモが保存値と一致する。未入力時刻を補完せず、トイレ・洗面の実施数は載らない。 |
| REP-02B | プレビューを再生成し、確認ダイアログをキャンセル | 永続化された`ReportVersion`と版番号は作られない。 |
| REP-03 | 結果画面の「報告」を押して確認ダイアログをキャンセル | 初回押下時刻を保存、送信版を作らない。7日の起算が始まる。 |
| REP-04 | 「報告」を再押下、または新版を再送 | 初回押下時刻は更新しない。 |
| REP-05 | 確認ダイアログの「完了」を押す | 最新の準備条件を再検査し、不変の版を1件作る。`202`時点で完了扱いにしない。 |
| REP-05A | 結果画面の本文を編集して「完了」 | APIの`confirmedBody`が報告版に固定され、報告IDなど必須要素を加えた最終本文と別に再表示できる。 |
| REP-05B | プレビュー後に備考本文や画像を変更して「完了」 | 作業内容の`sourceRevision`不一致で`409`。再プレビューと本文の再確認を求め、報告版・版番号を作らない。 |
| REP-05C | 確認前に添付画像の同期が終わっていない | `422`で送信を止め、端末内画像を保持。同期後に再確認すれば確定できる。 |
| REP-05D | 画像が同期済みの作業を確定 | 備考に添付した画像のID・ハッシュ・保存物参照を`ReportImageSnapshot`へ固定する。後の作業編集で過去版は変わらない。 |
| REP-06 | 「完了」を連打、同じ冪等キーで通信再試行 | 版とChatwork投稿を重複作成しない。異なる本文で同じキーなら`409`。 |
| REP-07 | Chatwork投稿成功を受ける | 版が`Sent`、作業が`Completed`になり、投稿ID・成功日時を保存。 |
| REP-08 | 明確な401・403・429等の送信失敗 | `Failed`。作業は完了にならず、再送時は新しい版。資格情報をレスポンスに出さない。 |
| REP-09 | 投稿タイムアウトで結果不明 | `Unknown`と独立した不明事実を保存。作業は`VerificationNeeded`。自動再送しない。 |
| REP-10 | 当日担当職員またはIT担当者が不明結果を投稿済みと確認 | 確認者・日時・根拠を保存し、版`Sent`、作業`Completed`へ移る。 |
| REP-11 | 同じ2種の確認者が未投稿と確認 | 根拠を保存し、版`Failed`へ移る。新しい版で再送可能。 |
| REP-12 | 権限のない利用者が結果不明を確認 | `403`。状態は変わらない。 |
| REP-13 | 成功済みの作業を修正して再送 | `sequence`が増えた新版を作り、旧版の本文・宛先・結果は不変。 |
| REP-14 | 作業日より後の日に送信を確定 | 過去日付の確認がないと`422`。確認後、ダイアログと送信内容に作業日・過去日付を明記。 |
| REP-15 | Markdown本文／`.md`添付、PDFを順に送信 | 設定どおりの形式で送る。本文モードでは`.md`を添付しない。 |
| REP-16 | アプリを開いたまま日本時間の0時を越える | 当日画面は新日の初期状態。前日記録は設定画面のアーカイブリンク先に現れ、内容は保持される。 |
| REP-16A | アプリを閉じて翌日に起動する | 当日画面は新日の初期状態。前日記録の作業日と入力は変えず、アーカイブから再開できる。 |
| REP-16B | 前日分がオフライン未同期のまま日付を越える | 前日分を削除・新しい作業日へ移記せず端末に保持し、新日の入力と区別する。接続回復後も元の作業日で同期する。 |
| REP-17 | 未押下下書きと送信済み記録を7日後に確認 | どちらも残る。送信済み版も再表示できる。 |
| REP-18 | 押下済みで未送信が確定した記録を押下から7日後に確認 | 送信済み版と保留中の版がなければ本文・入力結果を削除する。再送でも期限は延びない。 |
| REP-19 | 送信結果が`Unknown`のまま初回押下から7日経過 | 本文・生成物と必要な作業入力を保留し、アーカイブから確認できる。結果不明の事実記録も残る。 |
| REP-19A | 7日経過後に`Unknown`を`Sent`と確認 | 保留した本文・生成物を送信済み版として無期限保存し、作業を完了にする。 |
| REP-19B | 7日経過後に`Unknown`を`Failed`と確認 | 未送信版の本文・生成物を直ちに削除する。送信済み版がなければ作業入力も削除し、結果不明があった事実だけは残す。 |
| REP-19C | 7日経過時点で版が`Sending` | 結果が確定するまで`Unknown`と同様に内容を保留する。 |
| REP-20 | 送信済み版の後で作業対象を変える | 過去版の表示は送信時の対象箇所のまま。 |
| REP-21 | 初回送信成功後に作業を修正 | `WorkRecord`は`Completed`のまま。`hasSentReport=true`、`hasUnreportedChanges=true`を返し、再報告の準備判定を受けられる。 |
| REP-22 | 送信済み版がある作業の新版が`Sending`、`Unknown`、`Failed`になる | 旧版の送信済み実績と初回完了日時は不変。最新版の状態を別表示し、`Sending`・`Unknown`中の次版送信は`409`。`Failed`後は準備判定を通して新しい版を送れる。 |
| REP-23 | 新版が`Unknown`から`Sent`と確認される | `Completed`を維持し、最新版を`Sent`と表示。送信後に編集がなければ`hasUnreportedChanges=false`。 |
| REP-24 | 送信ワーカー停止で`Sending`開始から5分経過し、Chatwork投稿が見つかる | 1分間隔の監視または再起動後の回収で報告IDを照合し、追加投稿せず`Sent`にする。 |
| REP-25 | `Sending`開始から5分経過し、直近メッセージで投稿を確認できない | 不在だけで`Failed`と断定せず`Unknown`にし、不明事実を記録して人による確認を促す。自動再送はしない。 |
| REP-26 | `Unknown`移行後に遅い投稿成功応答が届く | 版IDと状態を照合して一度だけ`Sent`へ確定し、不明だった事実は残す。 |
| REP-27 | 未送信が確定した版の7日期限と画像削除 | ほかの作業・報告版から参照されない画像だけストレージから削除。送信済み版の画像は無期限、`Sending`・`Unknown`の画像は結果確定まで保留する。 |

## 5. マスタ変更と通知

別職員1名の承認取得を当日の担当職員が自己申告し、氏名を記録する。編集参加者と別の職員が内容を確認した翌日0:00（日本時間）に新版を適用する。

| ID | 操作・条件 | 期待結果 |
| --- | --- | --- |
| MAST-01 | 承認取得申告または別職員名なしで申請確定 | `422`。通知せず`Draft`を維持する。 |
| MAST-02 | 別職員1名の承認を得たと申告し氏名を記録して申請確定 | `Ready`から通知へ進む。承認者本人のアプリ操作は要求しない。 |
| MAST-02A | ログイン利用者が他人の作業ID・担当職員名で変更を申請 | 作業作成者IDと当日担当職員名の照合に失敗し、確定できない。 |
| MAST-03 | 通知開始直後 | `AwaitingNotification`。新版はまだ有効でない。 |
| MAST-04 | 日本時間23:59台に投稿と成功確認が完了 | `Notified`として記録。翌日になっても新版を自動作成・適用しない。 |
| MAST-05 | 日本時間0:00以降に再通知が成功し同日に確認 | 実際の投稿日と成功確認日時を別々に記録。通知日を基準に新版を自動適用しない。 |
| MAST-06 | 初回通知が明確に失敗 | 更新者本人だけにアラート。5分後に1回目の再通知を予約。 |
| MAST-07 | 失敗が続く | 5分間隔で最大2回だけ再通知。合計3試行で不成立、新版なし。 |
| MAST-08 | 処理停止などで`AwaitingNotification`が続き、月曜の投稿を水曜に変更IDで発見 | 投稿日は月曜、成功確認日は水曜と別々に保存。追加投稿せず`Notified`にする。木曜以降も新版は自動適用せず、マスタ照会結果は変わらない。 |
| MAST-09 | タイムアウト後、照合で見つからない | 内部結果`Unknown`を残し、履歴は失敗扱い。次の再通知を予約。 |
| MAST-10 | 通知失敗のアラートを別利用者が一覧取得 | 本人以外に出ない。 |
| MAST-11 | 最終結果から7日経過 | 通知・試行履歴を削除。変更・承認記録は残る。 |
| MAST-12 | 変更確定から1年経過 | 承認・変更記録を保存期限に従って削除。ただし報告再現に必要なマスタ版は維持。 |
| MAST-13 | アラート確認後30日、未確認のまま作成後1年 | それぞれの期限で削除。確認しても最長1年を超えない。 |
| MAST-14 | 同じ元版から作った2件を同時に`submit` | 1件だけが変更枠を確保し通知へ進む。もう1件は`409`でChatworkへ何も送らない。同じ適用日の別版を作らない。 |
| MAST-15 | 1件目が`AwaitingNotification`の間に2件目を`submit` | `409 active_change_exists`。1件目の通知結果が確定してから再申請できる。通知済み申請は申請日時順に表示する。編集更新番号が古ければ`409`。 |
| MAST-16 | 古い元版の下書きを、別途確認・適用された新マスタ版の成立後に`submit` | `409 stale_base_revision`。現行マスタを上書きせず、通知しない。 |
| MAST-17 | `ChangeFailed`後に過去の投稿の証拠が見つかる | 旧変更を自動復活・遡及適用しない。証拠を監査記録に残し、必要なら新しい変更として承認手続きをやり直す。 |
| MAST-18 | `ChangeFailed`後にIT担当者が投稿IDと変更IDを照合して証拠を登録 | `LateNotificationEvidence`に投稿・発見日時、確認者、非適用理由を保存。元の変更状態と有効マスタは変えない。同じ変更ID・投稿IDの重複登録を防ぐ。 |
| MAST-19 | 通知履歴を7日で削除し、変更内容を1年で削除した後に証拠を発見 | `MasterChangeOutcomeAnchor`の最終結果を照合して証拠を登録できる。証拠は発見から1年参照でき、元の氏名・変更内容は復元しない。 |

| MAST-20 | 通知済みの申請を確認 | 通知成功だけで編集・内容確認・更新が完了したと表示しない。 |
| MAST-21 | 通知済み候補をログイン職員が編集 | 編集者IDと時刻、更新番号を記録する。別職員の古い更新番号による上書きは`409`。 |
| MAST-22 | 編集参加者が確認しようとする | `403`。別の未編集職員だけが確認できる。 |
| MAST-23 | 未編集職員が差分と完成版を確認 | 確認者ID・日時・候補ハッシュを固定し、翌日0:00（日本時間）の予約版を作る。通知時刻を起点にしない。 |
| MAST-24 | 確認後に候補を編集 | 確認を無効化し、再確認まで予約版を適用しない。 |
| MAST-25 | 予約版の適用前後に作業を開始 | 適用前は旧版、翌日0:00以降は新版。開始済み作業は旧版のまま。 |
| MAST-26 | 同じ元版または適用日時で確認が競合 | 片方は`409`。古い申請は新たな申請と別職員の承認からやり直す。 |
| MAST-27 | 申請者が理由付きで適用前に取下げ | 新版は適用せず、予約版と確認記録を監査用に残す。適用後の取下げは`409`。 |
